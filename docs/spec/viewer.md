# Relic: the viewer

This document fixes how the viewer routes, renders, isolates, and what the recipient sees in every state. `docs/frame.md` and `docs/preconditions.md` are locked inputs. `docs/spec/format.md` owns the URL, the relic ID, and the container, and everything it settled is honored here rather than restated or reopened.

The 2026-11-10 decision in `docs/decisions.md` supersedes the original
100 MiB publication cap, prefix-only large-text behavior, and whole-file
memory tiers described by earlier revisions of this document.

One framing runs through the whole document and decides most of the hard cases on its own:

> **The viewing origin never lets attacker bytes choose what markup gets built.** It may place them into text nodes, and it may run a renderer whose element and attribute set is fixed regardless of input. **Any path where attacker bytes select elements, attributes, or URLs runs on the usercontent origin.**

The middle clause is doing real work, and §3.3 is where it earns its keep: a syntax highlighter builds structure out of attacker bytes and stays on the viewing origin anyway, while Markdown can't.

## 1. The four key-disclosure paths

Each is a case where every component behaves correctly and an unspecified boundary lets the decryption key walk out. They're written as rules, and every subsection below closes exactly one of them.

1. **Attacker bytes become markup on the viewing origin**, and that markup reads `location.hash`. Closed by 1.1 through 1.5, by 1.9, and by §3.1 putting Markdown on the usercontent origin.
2. **A blob URL built from attacker bytes gets navigated to on the viewing origin**, inheriting it, so a document the viewer never authored runs there. Closed by 1.6.
3. **A redirect without a fragment hands the key to its target**, with no bug in any component. Closed by 1.7.
4. **The viewing origin writes the key or the ID down**, into a `Referer`, a console line, storage, or an error object. Closed by 1.8.

### 1.1 The renderer class never routes

`format.md` §3.6 settled that the container carries no renderer class. While the class now reaches the viewing origin's document `<head>` as Open Graph and Twitter Card metadata for link unfurls, it never routes the viewer, and the viewer has no class to route on and must not ask for one or read it from the document head.

For a private relic the class is not shown in the shell. Its card is the generic private card (6.2), and nothing in the shell names a renderer class (plan 4.13).

The reasoning gets stated here because an earlier version of the recorded knowledge got it backwards and somebody will re-derive it. The class is a publisher assertion. If the viewer routes on it, a publisher declares `image` on an HTML payload and wins inline rendering on the origin holding the fragment, and that content reads `location.hash`. Fragment theft in one step.

What actually protects routing is `routeFor`'s inputs, which are the envelope header inside the AEAD plus a sniff of the decrypted bytes, resolving disagreement to the least privileged tier; the class is not a parameter of that function. A test on the built viewer bundles verifies that the viewer code never reads the card metadata from the DOM.

**Publisher-attestation inside the ciphertext does not fix this.** Attestation defeats operator forgery. It does nothing about a publisher lying, and the publisher is the threat. A malicious publisher signs an honest-looking lie, and the AEAD tag proves only that the operator didn't alter it.

### 1.2 Routing comes from magic bytes, and a hint can only ever downgrade

Routing comes from magic-byte sniffing performed after decryption, in the browser, treated as a hint that can only reach a **less** privileged path.

Privilege order, least to most: **download-only, then the usercontent origin, then the viewing origin.** Within the usercontent level, HTML and JSX sit together at the top, because both execute, and in the class-level ordering the disagreement rule consumes, `jsx` ranks with `html` at the most-privileged end and loses every disagreement it takes part in, exactly as `html` does.

That ordering is the whole safety argument. A hint that can only move content down the order is a hint an attacker gains nothing by forging. Any rule below that honors a publisher assertion honors it only because the assertion moves content downward.

**The order ranks browser-side privilege, never harm.** Download-only sits at the bottom and still puts a file on the recipient's disk under a name and extension the attacker chose, outside the sandboxed frame, from a Relic-branded page. So the safety claim is scoped: **an attacker gains nothing in the browser by forging a hint downward.** What they gain outside it is bounded by 1.9's filename rules and 1.3's mismatch copy, not by this ordering. Nobody downstream reads "least privileged" as "harmless."

### 1.3 The disagreement rule

The declared type is the **filename and declared mimetype in the encrypted envelope header** (`format.md` §3.1), decrypted out of record 0 before a byte of content renders. There's no class, and the envelope header is the better input anyway: it sits inside the AEAD so it's tamper-evident against the operator, and it's finer-grained, so a declared `.png` against HTML magic bytes is a sharper disagreement than `image` against HTML would be.

The rule operates on privilege levels rather than on type names. Map each of the two types to the level it would reach, then:

1. **If the two levels differ, the content is download-only.** Not the lower of the two: download-only, every time. A disagreement proves one input is lying and the viewer can't tell which, so every level above download-only means trusting one of them and download-only is the only path that trusts neither. A file named `chart.png` that sniffs as HTML isn't an image and doesn't reach the usercontent origin either, because sending it there would be trusting the sniff over a declaration it just contradicted.
2. **If the two levels are the same, there's no privilege disagreement, and the sniffed type picks the renderer.** The sniff comes from the bytes and the declaration is a publisher assertion, so where they agree on privilege the byte-derived one wins. Concrete: a file declared `chart.md` that sniffs as HTML lands on the usercontent origin either way, so the level is settled and the HTML renderer runs. Nothing is forged upward by this, because no type pair reaches the viewing origin with a markup renderer at all (§3.1).
3. **Either way the taskbar tells the recipient the contents don't match the name.** Clause 2 renders and still says so.

Three clauses, and they close the entire polyglot class for the first release.

### 1.4 Text without magic bytes, which is half the wedge

Markdown, plain text, source code, CSV, and JSON have no magic numbers. The sniff returns nothing for `{markdown, code}`, the class can't be trusted, and this is the hardest question in the unit. The rule:

1. **A silent sniff means untyped bytes, and untyped bytes get exactly one privileged treatment: plain text.** The gate: the bytes decode as valid UTF-8; C0 and C1 control characters outside tab, line feed, and carriage return mean binary, so download-only; a leading byte-order mark is stripped. **The bidirectional formatting characters are neutralized rather than passed through**, so `U+202A` to `U+202E`, `U+2066` to `U+2069`, `U+200E`, and `U+200F` render as visible escapes, never as controls. A UTF-8 check alone passes every one of them, and they reorder what a reader sees without changing a byte. That's Trojan Source, CVE-2021-42574, whose authors describe the attack as using "control characters embedded in comments and strings to reorder source code characters in a way that changes its logic" ([Trojan Source](https://trojansource.codes/)). Relic renders source code as its wedge, so this is the exact corpus the attack was written against.
2. **Valid text renders as plain text on the viewing origin, built as DOM text nodes.** This is safe by construction rather than by sanitization. Nothing parses the bytes, so content that's secretly HTML displays as HTML source and does nothing. That's the correct outcome, not a degraded one.
3. **The declared mimetype and filename extension may select a renderer within a level, or request a downgrade, and nothing else.** A `.py` extension picks a highlighter grammar. That is an attacker-selected parser running on the viewing origin, and calling it a decoration would be wrong. It's permitted for two specific reasons: whichever grammar runs, the highlighter's output element and attribute set come from a fixed set the viewer controls (§3.3), and an unrecognized hint falls back to plain text rather than guessing. A `.md` extension requests the Markdown path, which runs on the **usercontent origin** (§3.1), and honoring it is safe precisely because it moves content to a *less* privileged origin. A publisher who lies about `.md` gets the usercontent origin, which is where HTML already goes, so the lie buys nothing. A publisher who lies the other way gets plain text, which is a downgrade and harmless.
4. **An unrecognized hint falls back to plain text.** Never best-effort, never a guess.

### 1.5 SVG is download-only in the first release

SVG's execution is context-dependent. It's inert under `Content-Disposition: attachment` and inside `<img src>`, and it fully executes on direct navigation ([digi.ninja](https://digi.ninja/blog/svg_xss.php), which tests direct view as vulnerable and both `<img>` and attachment as not). Inline SVG is part of the host document's own DOM by definition, so it executes there too.

**A spec that says "still images render inline" without carving out SVG ships the CVE.** SVG is download-only in the first release. Usercontent-origin rendering for it is available later and isn't in scope now.

SVG has no magic number and sniffs as XML or text, so the sniff can't route it and the declaration has to. 1.4 rule 3 already permits that: **a declared `image/svg+xml` mimetype or a `.svg` extension is an explicit downgrade trigger to download-only**, legal because download-only is the least privileged path, so forging it gains nothing and declaring it honestly gets the safe outcome. Untyped bytes that happen to be SVG, carrying neither, are untyped bytes: plain text on the viewing origin under 1.4 rule 2, where nothing parses them and they display as XML source. No input reaches two different answers.

### 1.6 Blob URLs inherit the creating origin

The File API describes the inheritance in a section it labels informative: "The origin of a blob URL is always the same as that of the environment that created the URL, as long as the URL hasn't been revoked yet." The normative statement the rule below actually rests on is in the next section, on access restrictions: blob URL fetches are limited to environments whose storage key matches, and "Blob URL navigations are not subject to this restriction" ([File API](https://w3c.github.io/FileAPI/)). Navigation is exactly the dangerous path, and it's the one carrying the fewest guardrails.

- **Never navigate to, and never open in a new tab, a blob URL built from untrusted plaintext on the viewing origin.**
- **Download blobs are typed `application/octet-stream`** regardless of what the container declared, and they're triggered through an `a[download]` attribute. The container's declared mimetype never reaches `Blob`'s type argument.
- **Images render only via `<img src=blob:>`**, where parsing is inert.

### 1.7 Redirects, and the rule splits on where the redirect lands

RFC 9110 §10.2.2 makes fragment inheritance mandatory browser behavior: "If the Location value provided in a 3xx (Redirection) response does not have a fragment component, a user agent MUST process the redirection as if the value inherits the fragment component of the URI reference used to generate the target URI." The spec's own cross-origin example redirects `example.org/index.html#larry` to `example.net/index.html` and lands on `example.net/index.html#larry`, "preserving the original fragment identifier." §17.11 names the hazard: this "might have the effect of disclosing one site's fragment to another site," and a site using personal information in fragments "ought to ensure that redirects to other sites include a (possibly empty) fragment component in order to block that inheritance" ([RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)).

**Read the remedy's scope, because a blanket version of it destroys the key.** The RFC scopes the fix to redirects *to other sites* and documents inheritance as the desirable behavior everywhere else. The server never receives the fragment, so where the redirect stays inside Relic's own service, "explicit, possibly empty" can only mean empty, and an empty fragment is a deleted key: a recipient hitting `/{id}/#key` gets redirected to `/{id}` carrying nothing and lands on §6.1's "link is missing its key" screen holding a link that was never broken.

**So the split is on where the redirect lands, not on whether the origin changes**, and the two halves point opposite ways.

**Leaving the service, an explicit, possibly empty, fragment in `Location` is mandatory.** One fragment-less redirect to the usercontent origin hands it the key, with no bug in any component. Where it bites:

- **service origin to usercontent origin**, the dangerous one, and the whole reason the two-domain split exists
- **any CDN or load-balancer redirect the application doesn't author** that lands off the service domain, which is the one nobody audits, because it lives in infrastructure config rather than in code review

**Staying inside the service, the redirect deliberately omits the fragment so inheritance carries the key through.** This gets said out loud, because the blanket MUST reads as forbidding it and somebody implementing from a one-line summary will kill working links. It covers legacy or renamed paths, trailing-slash normalization, apex to `www` and back, and HTTP to HTTPS. The last two change origin without leaving Relic, and applying the other half to them would kill the key on every link typed or pasted without a `www` or a scheme. **The test is the destination's trust boundary, not its origin tuple:** the service origin and its host and scheme variants are all Relic, the usercontent origin is not, and that's the line the fragment must not cross.

**The preferred form is that no inside-the-service redirect exists on the relic path at all.** `format.md` §1.1 already issues none for ID case, and HSTS preload on both registrable domains moves the HTTP-to-HTTPS upgrade into the user agent, so no request and no redirect happens.

Redirects and rewrites performed by third parties, including link shorteners and enterprise link rewriters, belong to `spec-service-surface`.

### 1.8 Neither the ID nor the key gets written down

**The viewing origin sends `Referrer-Policy: no-referrer`.** The relic ID appears in that origin's own `Referer` on any outbound request (`format.md` §0), and this closes it. **That's an ID control and not a key control**, and the distinction is worth a sentence, because "the referrer policy handles it" is how somebody later concludes the fragment is covered and stops looking. Fragments are never sent in a `Referer` to begin with. `Referrer-Policy` was never protecting the key and can't.

**The key is closed by a separate rule: no code path writes the fragment or the key to the console, to storage, or into an error object.** Error objects are the leak nobody plans: a thrown error carrying the URL gets logged, serialized, or displayed, and the honest reason the viewing origin has no error reporting (a locked precondition) is that an error reporter is a same-origin script that reads whatever it's handed.

### 1.9 The filename is untrusted display text

`format.md` §3.1 states it flatly: the filename "is **untrusted display text**. It reaches the DOM as a label and gets used as a lookup key, the same defect class as archive entry names," carried as a bounded UTF-8 byte string that asserts nothing about itself. It's the one attacker-controlled stream that's guaranteed to reach user-visible text on the origin holding the fragment, because §1.3's mandated copy requires displaying it. Six rules:

1. **It enters the taskbar as a DOM text node, never as markup.** No markup interpolation, no attribute injection, no exceptions. This is 1.4 rule 2 applied to a field arriving outside the content stream, which is why it's easy to forget.
2. **It passes 1.4 rule 1's gate**, with the bidirectional characters stripped here rather than escaped. A filename has no legitimate use for them, and a right-to-left override in a label is how `report.exe` displays as `report.txt`.
3. **The taskbar bounds what it displays** and never lets a long name push the abuse-report link, the copy-link control, or the sandboxing notice off screen. Length is attacker-chosen too, and those controls are the ones a recipient needs most when something is wrong.
4. **The `a[download]` value comes from the filename, sanitized for filesystem use.** Path separators and traversal segments are removed, so the name can't escape the download directory or impersonate a system path. The extension stays attacker-chosen and the blob stays `application/octet-stream` (§1.6), so the browser won't execute it. The recipient might, which is what §1.3's mismatch copy warns about and why §1.2 scopes its claim to browser-side privilege.
5. **An empty filename is legal and means the viewer names the download from the relic ID** (`format.md` §3.1). Not a guess, and not an error.
6. **Reading the extension for §1.3 and §1.4 is a parse on the final dot only**, with no filesystem semantics. It's a lookup key derived from a hostile string, so it gets the narrowest reading available.

## 2. The usercontent origin's shape

**Decision: a per-relic subdomain, not one fixed content origin.**

**The cost a fixed origin appears to carry isn't real, and the argument has to rest on the one that is.** The obvious objection is that relic A's rendered content would share an origin with relic B's, so one malicious relic could reach another's rendered document. Under the two-layer boundary §4 mandates, every rendered document already sits in its own opaque origin, so two relics on a single hostname are already mutually cross-origin. The frame's sandbox flags answer that objection, not the hostname.

Per-relic subdomains are intended as defense in depth for rendered content.
Browser process isolation for sandboxed documents varies by engine and site
classification ([web.dev](https://web.dev/articles/securely-hosting-user-data)).
The large-source view and browser-managed Blob do not require the full
plaintext to sit in a neighboring frame.

Per-relic subdomains use the Immich pattern. The usercontent origin serves a
static shim; rendered content arrives from the parent rather than a
crawler-addressable content URL. The browser controls where the resulting
plaintext is backed, including any temporary storage (§5).

Four consequences:

- **The label is a one-way function of the relic ID, and it isn't the ID.** Using the raw ID would put a live bearer token for the ciphertext into every DNS query along the resolution path, broadly visible and replayable against the service. A truncated hash of a 122-bit-floor ID isn't invertible, so a passive DNS observer learns that some relic was opened and can't turn the label back into a fetchable ID. **The residual runs the other direction and gets stated.** The derivation is deterministic and public, so anyone already holding the URL can compute the label and confirm from a resolver log that a specific device opened that specific relic. Real capability, granted only to somebody who was already given the link, and the price of a stable origin.
- **Derivation is deterministic rather than random per render**, keeping the origin stable across repeat opens and the shim cacheable. Two recipients of one relic therefore share a shim origin. **What makes that safe is not that they're looking at the same content.** It's that both of their rendered documents sit in opaque origins regardless of hostname, so a shared shim origin gives neither of them anything.
- **The parent computes `targetOrigin` per render** from the derived label, and that survives §4's boundary intact: the shim sits on a real, nameable origin precisely so an exact `targetOrigin` exists. **The shim's expected parent origin stays a hardcodable constant**, because there's only ever one viewing origin.
- **The label must be a single DNS level**, since a wildcard certificate covers one label and not two.

**PSL registration of the usercontent parent is required and routes to `shape`** (§7). Repeating the preconditions' honest limit without softening it: treat PSL as origin isolation with a possible listing-scope benefit, never as a guaranteed firewall. No documentation confirms Google won't list at a PSL-registered parent anyway, and the Immich outcome was broader than the mechanism required.

**The usercontent origin may never sit under the RP ID.** A usercontent hostname equal to the service hostname, which is the WebAuthn Relying Party ID, or ending in `.` plus that hostname, is refused by `assertConfig` (plan 4.9, correction 20). The reason is the decryption path. A page on such an origin could request PRF output from a user's passkeys, and that output is the key-encryption key for a private identity (6.12). Any per-relic subdomain topology described above lives under the usercontent domain only, never under the service hostname.

## 3. Rendering each class

### 3.1 Markdown renders on the usercontent origin

Markdown is a partial HTML class, because Markdown permits raw inline HTML. Rendering it on the viewing origin puts sanitizer output next to the fragment.

The two candidates were stripping raw HTML entirely and rendering on the viewing origin, or rendering on the usercontent origin exactly like HTML. **The choice is forced rather than balanced.** A locked precondition says origin isolation is the first layer and sanitization "is never the only one." Markdown must generate markup structure from attacker bytes no matter how raw HTML is handled, and its `href` and `src` values come straight from the source, so rendering it on the viewing origin makes sanitization the only layer standing between an attacker and the trusted origin. That's the thing the precondition forbids.

Note what stripping raw HTML does not buy. It narrows the surface to the Markdown parser's own escaping of text and URL attributes, and mXSS is precisely the class that defeats that narrowing.

**Wherever sanitization runs, it's pinned past every advisory known at build time, and it's never the only layer.** The evidence for treating that as a standing rule rather than a nicety is CVE-2026-41238, which affects DOMPurify "3.0.1 through 3.3.3 (latest)" with 3.4.0 patched, CVSS 6.9. One qualification the shorthand loses, and it changes how much weight the citation carries: the advisory's prerequisite is that an "Attacker must have a prototype pollution primitive in the same execution context." So the sanitizer isn't independently bypassable here. What is true is that no special configuration is needed, and a prototype pollution gadget anywhere else in the same context converts a standard `sanitize(userInput)` call into a full bypass ([GHSA-v9jr-rg53-9pgp](https://github.com/advisories/GHSA-v9jr-rg53-9pgp)). Which sanitizer gets used is `shape`'s call, along with the rest of the stack. That it's never load-bearing on its own is this document's.

**The source toggle lives across the origin boundary.** `frame.md` locks the first release as rendering Markdown with a source toggle, and the two sides land on different origins. Raw Markdown source is plain text, so by §1.4 rule 2 the **source view renders on the viewing origin** as DOM text nodes, optionally highlighted under §3.3's rules. The **rendered view is on the usercontent origin.** So the toggle switches which origin is showing, not which mode a single frame is in. The taskbar owns the control, because the taskbar is the only surface that spans both. The parent already holds the plaintext, so the source view costs no round trip. **Switching away from rendered tears the shim frame down, and switching back re-posts the payload with a fresh render nonce**, so a relic can't keep a live frame running behind a source view the recipient thinks is the whole page.

For Markdown larger than 100 MiB, the windowed source view in §5 replaces
the full rendered view and source toggle.

**This changes the usercontent origin's role from "HTML only" to "all rich text."** The `postMessage` surface carries a routing type covering both, and the split of the viewer across domains is: the viewing origin owns fetch, decrypt, JSX transpiling (§3.5), the taskbar, the download blob, plain text, highlighted code, the Markdown source view, and raster images; the usercontent origin owns everything that becomes markup and everything that executes.

### 3.2 Link and image targets are attacker-controlled

Markdown link and image targets are attacker input: `javascript:`, `data:`, and remote images. A remote image is both an exfiltration channel and a beacon revealing that a specific relic was opened.

Under the locked strict CSP they fail to load. **The viewer explains why.** Silent broken-image icons read as a corrupt file, and the recipient blames the publisher while the publisher blames the product. The shim reports blocked external resources in its ack (§4), and the taskbar states that this relic asked for external resources and Relic blocked them.

### 3.3 Code and plain text, two traps

**Highlighter input.** Syntax highlighters take a language hint usually derived from the attacker-controlled extension, and some build HTML by string concatenation. **Build highlighted output as DOM text nodes**, creating elements programmatically and assigning `textContent`, so attacker bytes never reach a markup parser. **On an unrecognized hint, or a highlighter that can't work that way, the fallback is plain text.** There is no sanitize-then-parse fallback on the viewing origin. §3.1 invoked a locked precondition to forbid exactly that, and an escape hatch here would reopen it one section later on the same origin.

**Why code stays on the viewing origin while Markdown doesn't, stated precisely**, because the easy version of this distinction is wrong. A highlighter does build structure out of attacker bytes: it emits `<span>` elements whose boundaries are chosen by the input. The difference is in what the input can choose. **A highlighter's element set and attribute set come from a fixed grammar the viewer controls**, so whatever the bytes say, the output is spans carrying class names from the viewer's own theme, and nothing else. **Markdown's `href`, `src`, and raw-HTML passthrough are attacker-controlled by design.** That's the line, and it's the second clause of the framing at the top of this document.

**Pathological input.** A code file can be many megabytes on one line, which hangs the highlighter and freezes the tab. **Cap the highlighted region and render the remainder as plain text behind a stated cutoff**, with the cutoff visible to the recipient rather than silent. The cap's value goes to `shape` (§7).

### 3.4 Where security headers actually matter

The object fetch runs client-to-GCS on a signed URL, so the app server can't set headers on it, and what GCS serves is ciphertext, indistinguishable from random and unsniffable into anything executable. `nosniff` on the bucket guards almost nothing.

**The controls that matter are the viewing origin's own responses, the shim's own response, and the blob URLs the viewer creates.** Stating it here stops a later station spending its effort on bucket headers that guard nothing while skipping the viewer-side ones that guard everything.

### 3.5 JSX renders on the usercontent origin, transpiled on the service origin

`jsx` is the eighth renderer class, reached by the `.jsx` and `.tsx` extensions. It renders on the usercontent origin for the same reason HTML does: it executes. Honoring the extension is a downgrade under §1.2's rule, because untyped bytes otherwise get plain text on the viewing origin, which is the most privileged path there is, and the usercontent origin sits below it. A publisher who lies about `.jsx` gets their bytes executed in an opaque origin that cannot read the fragment, which is the outcome the ordering exists to produce.

**Transpile on the service origin, execute in the frame, and the split is the whole safety claim.** The viewer bundles a transpiler into its own service-origin code and transforms the decrypted JSX string into plain JavaScript as a text operation: bytes in, bytes out, nothing evaluated. The service origin, the one that holds the fragment until §2.5 strips it, never executes untrusted code, and that is what keeps the frame's first locked constraint intact now that a rendering path executes by design. The transpiled code is posted to the usercontent frame as `{ type: 'relic:render-jsx', code: string }`, a sibling of `relic:render`, and the one-render-only guard applies to it exactly as it does to `relic:render`: anything that can post to that frame could otherwise swap the content after the recipient has decided to trust what they are looking at.

**React is bundled into the frame's inlined bundle, and nothing is fetched from a CDN.** An earlier revision of this section had the frame importing React from a permissive CDN, because the render frame is an opaque origin, its module fetches are CORS requests carrying `Origin: null`, and Relic's own origins do not answer those while a permissive CDN does. Closing egress removed that middle ground: a policy that permits no remote source permits no CDN either, and in an opaque origin `'self'` matches nothing, so the frame cannot fetch even its own assets. Same-origin assets are the one thing this origin structurally cannot reach, which forces the only remaining answer: React is inlined into the `sandbox.html` response at build time and reaches transpiled component code as the global `globalThis.React`. The transpiler emits classic-runtime `React.createElement(...)` calls, which resolve against that global, so the mounted module needs no import statement at all.

**The frame has no network reach, and the property is measured rather than argued.** The response that builds the frame carries a policy permitting no remote source of any kind, and under it `fetch`, `<img>`, `sendBeacon`, `WebSocket`, and `EventSource` all produced zero arrivals at a collector server, so whoever authored a JSX or HTML relic has no channel to the recipient through the rendered content. Two probe results are stated with their caveats, because each can be read as proving more than it does. `sendBeacon` returned `true` while delivering nothing, so its return value is not evidence. `window.open` was blocked in the probe, but no user gesture was present, so the policy is not what stopped it; popups are removed by dropping the `allow-popups` flag from the sandbox attribute, which leaves `allow-scripts` and nothing else. A form with `target=_blank` submitted and never arrived, blocked by `form-action 'none'`. What remains true of the boundary itself: the frame is opaque, holds no credentials, cannot read the fragment on the viewing origin, and cannot reach anything of Relic's. The cost is named rather than absorbed: a page or component that references a CDN stylesheet, a CDN script, an external font, or a remote image renders without it, and publishers must inline what their page needs (§6.3).
A reader clicking an external link is not rendered-content network reach. The
frame prevents its own navigation and sends only a canonical `http`, `https`,
or `mailto` destination across the existing message boundary after a trusted
click. The parent validates it again and opens a separate tab with `noopener`
and `noreferrer`. Author code still cannot fetch, beacon, navigate, or open a
popup, and a scripted click is rejected.


### 3.6 OpenTimelineIO native playback and timeline viewer

**Proposed native timeline player.** Subject to end-to-end surface proof in `packages/relic-mcp/test/otio-path.ts`.

`otio` is the tenth renderer class (`RendererClass: otio`, `CLASS_BEHAVIOUR.otio: plays`, `RenderRoute: otio`).

- **Archive routing and sniffing:** Decrypted content is inspected by byte signature and archive index. Standard `.otioz` archives (containing `content.otio` and `version.txt`) route to `otio`. Generic archives remain download-only (`CLASS_BEHAVIOUR.archive: downloads`). A raw `.otio` file provides structural inspection without remote fetching.
- **Viewport layout and timeline navigation:** The OTIO stage fills its parent after any version notice. The preview and desktop inspector share the remaining height above playback, the compact timeline, and the In/Out/Comment/Clear readout. The canvas fits both available dimensions without cropping or changing its intrinsic rendering resolution. The timeline scrolls internally on both axes, with a height capped at the smaller of 240px and 30% of the OTIO pane; the 760px minimum grid and sticky track labels remain. Inspector content, blocked-preview details, and diagnostics scroll inside their bounded regions. On mobile, Inspector opens as an opaque, nonmodal disclosure over the upper OTIO surface, capped at the smaller of 22rem and 60% of the pane. Its tabs and Close inspector action remain visible while source context scrolls. Opening it preserves preview dimensions, selection, playback position, and timeline scroll. Close and Escape return focus to the Inspector toggle. Comment closes the mobile inspector before revealing its attached composer. Selection and posted-marker exposure is clipped to the timeline client area, stage client area, and viewport, excluding sticky labels horizontally. Explicit Comment and sidebar reveal actions scroll only the timeline to the exact target; passive scrolling retains the reader's position. The comment editor remains a target-attached popover, not a permanent dock.
- **Composition and multi-track playback:** Evaluates timeline tracks in painter order (video stacked bottom to top over opaque black; audio summed additively across all active tracks). Gaps are transparent for video and silent for audio. Disabled items change contribution without altering timeline duration. Nested stacks evaluate parent coordinate systems without spilling.
- **Time ranges and rational time:** Rational time `{value, rate}` is preserved across all coordinate systems. Mixed rates, non-zero start times, and source trims are supported natively.
- **Transitions and retiming:** Evaluates `SMPTE_Dissolve` transitions by blending premultiplied track contributions into an intermediate track surface before stacking. Evaluates `LinearTimeWarp` scalar retiming and freeze frames. Image sequences (`ImageSequenceReference`) resolve frames from bundled media with frame step and missing frame policies.

Movie samples outside their available range are withheld for video and silent for audio. When paused, scrubbing, or seeking, video decoders seek the exact midpoint of a certified presentation window, preserving the sampled frame at decoder boundaries. During continuous playback, decoders run continuously under native decode whenever admitted to native mode, falling back to exact midpoint seeks when native admission is unmet. Before an image sequence begins, `hold` selects the first archived frame, skipping missing entries; after its end it still selects backward.

- **Certified movie timing:** Movie timing comes only from actual, sorted packet-presentation windows in the local bundled Blob. For a source sample, the viewer binary-searches window starts with rational comparison in that sample's units and confirms the half-open end. For paused inspection, transport seeks, and scrubbing, it seeks the certified window midpoint. When the browser exposes a classifiable VideoFrame timestamp, it paints only a frame matching the certified window. If the decoder continues to present another window, the leaf is withheld with an `invalid-timing` diagnostic. Browsers without a usable frame timestamp retain the unverified element paint. It never reconstructs an FPS grid, shifts the first PTS to zero, or treats OTIO units as media cadence. An unknown index, window gap, or uncovered sample seeks exact normalized source seconds and reports `invalid-timing` rather than guessing. A representationally negative value that compares equal to zero is normalized only in decoder-local state; true negatives and missing handles remain withheld or silent.
- **Timing limits and certified spans:** The timing reader's file-size and total-read limits are 500 MiB; one playback controller retains at most 16 MiB of timing arrays. Packet, index, scheduler, codec, and other parser limits remain separate. Reader caps return an explicit unknown result rather than a partial index. The scanner certifies a single contiguous presentation span from the first packet start to the final packet end: `[starts[0], ends[last])`. An uncertified tail is omitted from the index.
- **Playback modes and continuous native decode:** Continuous native playback activates only when every drawn video leaf passes native admission: certified presentation windows (`timing.kind === 'windows'`), every window duration and every gap between packet starts greater than 2Q (`Q = 2e-6` seconds), `requestVideoFrameCallback` and `VideoFrame` available, rate application succeeds, the smallest presentation window divided by rate is at least the display refresh interval, the media path has not been marked runtime-ineligible, and the snapshot budget permits. Freeze frames and still images are static and admitted; image sequences run on seek cadence. When any drawn video leaf fails native admission, the composition falls back to seek cadence, preserving exact midpoint seeks and existing diagnostics.
- **Snapshot ring and synchronous callback capture:** Each native decoder maintains a fixed ring of three reused snapshot canvas surfaces sized to the output (960x540). They are allocated once on entering native mode, reallocated only on canvas resize or canvas context loss, and freed on release, counting against `OTIO_RETAINED_SNAPSHOT_PIXELS`. No canvas, bitmap, or ImageData allocations occur per frame. Inside `requestVideoFrameCallback`, the callback checks the current controller and epoch; stale callbacks return without re-registering. Tagging matches the captured frame's own timestamp (microsecond whole numbers, Q = 2 microseconds retained, `Q = 2e-6` seconds) from `new VideoFrame(video)` against packet start times rather than callback metadata. If two packet starts fall within 2Q, the media is ineligible. On a match, the video frame is drawn synchronously into the oldest ring slot before the element can advance, tagged with packet index `k` and lead, and re-registered; the `VideoFrame` is closed in a finally block.
- **Certified-span tail rule:** Callbacks outside the certified contiguous span (`mediaTime < starts[0] - Q` or `mediaTime >= ends[last] - Q`), such as decoders running ahead into uncertified tail frames or lead-in, are ignored: no capture, no tag, no sticky ineligibility mark, and no resync. Inside the certified span, an unmatched callback is an uncovered presentation. Any uncovered callback during startup or two consecutive uncovered callbacks marks that media path sticky-ineligible for native playback. When transport required time reaches an uncertified sample (`certifiedWindowIndex` returns null), the leaf becomes uncertified at T. This triggers an eligibility discontinuity: one exact resync into seek cadence, seeking exact normalized source seconds and reporting `invalid-timing`. The uncertified tail frame is never approved for native display. Eligibility-driven fallback applies only to the current drawn set and re-evaluates at each discontinuity, returning subsequent certified clips to native playback.
- **Approval gate and hold:** At transport tick time T, the required presentation window index `req` for each drawn native leaf is derived via rational half-open search. The composite paints and advances `currentTime` only if every drawn native leaf has a ring slot tagged `req` in the current epoch, and all static leaves are ready. If any drawn leaf lacks its required frame, the compositor holds: the previous composite remains on screen, and `currentTime` and `notify` do not advance. The compositor never paints a playing video element directly; it renders only approved snapshots through the multi-track compositor. Controller `notify` fires at most once per tick, on repaint or a new timeline frame.
- **Discontinuities, phase anchoring, and bounded resync:** Discontinuities trigger on play, seek, resync, canvas context restore while playing, and any change to the set of drawn occurrences or their eligibility. A discontinuity freezes the transport, pauses decoders and audio elements, increments epochs, runs exact `renderAt(T0)` (seeking leaves to midpoints and audio to exact positions), and starts playback on drawn media. Transport phase anchors once per start in closed form from the measured arrival of the first advanced frame callback across all drawn native decoders. If the phase spread across decoders exceeds the tolerance band, it retries once, then drops to failure-driven seek cadence until the next play or seek. Every change to the set of drawn occurrences triggers one exact resync. Montage churn and unstable tracks are bounded: more than 3 drawn set changes within 5 s, or 3 failure resyncs within 10 s, switch playback to seek cadence until the next play or seek.
- **Audio synchronization in both modes:** Steady audio drift is evaluated against the current tick target with a tolerance of 2 timeline frames, rather than the reciprocal of the audio source rate. Drift corrections execute as asynchronous seeks with gain set to 0 until the `seeked` event fires, never blocking transport ticks. Discontinuities execute an exact seek and resume playback.

- **Fidelity boundaries and diagnostic states:** Browser playback operates in browser-managed SDR. Unsupported effects, proprietary plugins, unknown schemas, and unavailable codecs trigger explicit diagnostic states (`supported`, `missing-media`, `unsupported-codec`, `unsupported-effect`, `unsupported-schema`, `invalid-timing`, `unsupported-browser`). An incomplete preview provides a deliberate "Preview base media without unsupported effects" control; it is never claimed as full fidelity.
- **Security:** The viewer never executes bundled code, plugins, or SchemaDef expressions. All media references resolve only to existing non-directory entries beneath bundled `media/`; remote network fetches are barred.
- **Chunk loading:** The OTIO parser and playback engine are lazy-loaded on demand to preserve the initial viewer shell budget.

### 3.7 STL and OBJ model inspection

The `model` renderer class is public metadata and never selects the viewer route. The viewer uses the encrypted name and MIME together with a byte-derived candidate, then validates geometry in a bounded worker. Conflicting declarations fall back to download.

The viewer displays binary and ASCII STL and geometry-only OBJ. It does not load materials, textures, external files, URLs, or author code. Model coordinates are expressed in file units. Whole-relic comments and version history remain available; screen-relative model annotations and side-by-side model comparison are not supported. Original bytes remain available for download.

The interactive parser admits at most 16 MiB, 250,000 triangles, 500,000 source vertices, and 1,024 vertices per face. Invalid, unsupported, or over-limit files must produce an error with the original download available. A parser worker can be terminated, but is not an isolation boundary against arbitrary code execution on the viewing origin.

## 4. The sandbox boundary

**Direction is forced, not chosen.** The main origin fetches, decrypts, and posts plaintext to a static shim whose own code never touches ciphertext and never makes a request. The alternative shape, where the usercontent origin fetches and the parent posts it the key, is what somebody reaches for to avoid moving large payloads across a boundary, and it requires the key to cross. That must never happen.

**The boundary is two layers, because an opaque origin has no address.** The obvious shape is one frame carrying `Content-Security-Policy: sandbox` on its own response. It doesn't work, and the reason gets stated because somebody will reach for it. MDN is exact about what that header does to the framed document: "A sandboxed resource is otherwise treated as being from an opaque origin, which ensures that it will always fail same-origin policy checks... The Origin of sandboxed resources without the `allow-same-origin` keyword is `null`" ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/sandbox)). An opaque origin matches no `targetOrigin` a parent can write, and `"null"` isn't a URL `postMessage` can parse, so the only value that reaches such a frame is `'*'`. That's the one value the payload message must never use. **Sandbox the shim's own response and you've forced the exact leak the rule below exists to prevent.**

So the boundary is split, which is what the pattern §2 cites actually describes: the product frames a shim at `$RANDOM_VALUE.exampleusercontent.com/shim`, posts the untrusted content in, and "the rendered content is transformed to a Blob and rendered inside a sandboxed iframe" ([web.dev](https://web.dev/articles/securely-hosting-user-data)).

- **Layer one, the shim.** A static file on the per-relic usercontent origin, served on a real origin with no `sandbox` on its own response, so the parent can name it with an exact `targetOrigin` and it can name the parent with one. It's first-party code Relic authors. It never touches ciphertext, never touches the key, and its own code makes no requests. The documents it renders make no requests either: the response policy permits no remote source (§3.5), so no bytes leave the recipient's browser as a relic's fetch, and the origin still serves one static file whose own code makes no requests. Its own response carries `default-src 'none'` with its single inline script admitted by hash, `frame-ancestors` limited to the viewing origin, and `X-Content-Type-Options: nosniff`.
- **Layer two, the render frame.** The shim builds the untrusted document and renders it in a child iframe carrying the `sandbox` attribute. That's where the opaque origin belongs and where it costs nothing, because nothing needs to address the render frame by origin. **Never both `allow-scripts` and `allow-same-origin`**, which is locked in the preconditions. The attribute is `allow-scripts` and nothing else, and outbound requests are blocked by the frame document's response policy rather than permitted: `default-src 'none'; script-src 'unsafe-inline' blob:; style-src 'unsafe-inline'; img-src data: blob:; font-src data:; media-src data: blob:; worker-src 'none'; form-action 'none'; base-uri 'none'; frame-ancestors <service origin>; webrtc 'block'`. No fetch directive names any host. `blob:` stays in `script-src` for the JSX mount's blob module, which is local and involves no network; `data:` and `blob:` in the image and media directives carry the viewer's own decrypted bytes. Because Chrome does not enforce CSP `webrtc 'block'` over ICE candidate gathering, the viewer installs a runtime deny-list that neutralizes WebRTC APIs (`RTCPeerConnection`, `webkitRTCPeerConnection`, and transport constructors) across the global prototype chain and denies nested frame creation (`iframe`, `frame`, `object`, `embed`, `portal`) so author code cannot spawn an unpatched realm. This containment is a tested runtime deny-list in the frame's JavaScript realm rather than an architectural impossibility: future platform APIs could reopen egress before we patch them, and nested frames or workers in HTML and JSX relics are denied as the accepted cost. The frame's script is inlined into the response rather than fetched, because an opaque origin cannot fetch from anywhere, not even Relic (§3.5). What the opaque origin still contributes is the rest of the confinement: no credentials, no storage, no same-origin relationship with anything, and no path to the viewing origin's fragment. Nobody reads this layer as confinement of the recipient's network; it is confinement from the recipient's network.

**The attribute is sufficient at layer two, and only because the never-both rule holds.** The usual reason to prefer a header is that a framed document can otherwise strip the `sandbox` attribute off its own iframe element and reload, dropping every restriction. Doing that means reaching the embedder's DOM, which means `allow-same-origin`. Without it the render frame is opaque and can't touch the shim's document at all. The two rules are load-bearing together and neither is optional. **That's derived from the mechanism, not quoted**: no page makes the header-versus-attribute comparison, and citing one for it would be a citation that doesn't say what it's cited for.

**What crosses.** Parent to shim: the decrypted bytes, the routing type, and a render nonce. Never the key, never the fragment, and not the relic ID. The shim needs none of it. The per-relic subdomain label already gives the usercontent document a stable per-relic pseudonym, which is exactly why §2 makes that label a one-way function: the shim can correlate its own renders and can't derive the ID.

**PRF is evaluated only on the service origin, in the parent document.** The render frame is an opaque origin where WebAuthn cannot run, and section 2 keeps the usercontent origin out of the Relic RP ID. Decryption happens in the parent, so PRF output and every key derived from it stay there. Nothing crossing this boundary carries PRF output, a key, or extension results. The serializers in `passkey-common` never include `clientExtensionResults`, and nothing calls `PublicKeyCredential.prototype.toJSON` (plan 4.4, correction 19).

Shim to parent: a `ready` handshake, a rendered-or-failed ack that names blocked external resources, and optionally a requested height.

**The handshake.** The shim posts a data-free `ready` to `parent`. The parent replies with the payload and an **exact** `targetOrigin`, computed per render from the derived label. The shim pins `event.origin` from that reply and ignores everything else. Because §2 makes the shim's expected parent origin a hardcodable constant, **the `ready` uses that exact origin too**, and `'*'` appears nowhere in the design. MDN is direct about why: "Always specify an exact target origin, not `*`, when you use `postMessage` to dispatch data to other windows. A malicious site can change the location of the window without your knowledge, and therefore it can intercept the data sent using `postMessage`," and on the receiving side, "always verify the sender's identity" using `origin` ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage)).

**The payload message must never use `'*'`.** A `postMessage` with target `'*'` carrying a decrypted relic hands the whole plaintext to whatever occupies that frame, which is worse than leaking one relic's key. `'*'` is tolerable only on a message carrying no data at all, and the two-layer shape means no message needs it.

**The render frame gets a free discriminator out of this.** It's opaque, so anything it posts to the shim arrives with `event.origin` of `"null"`, which the shim's pinned parent origin can never equal. So a message from the render frame is never mistakable for a message from the parent, and the shim treats every one of them as attacker input.

**Untrusted numbers.** A requested-height channel is a message type an attacker also gets to send. The parent treats the value as untrusted input: it rejects anything non-finite, negative, or non-numeric, clamps to a range bounded by the viewport minus the taskbar, and rate-limits the message so a relic can't drive a resize loop. A relic can't make itself taller than the viewport.

**Copies across the boundary.** Rendered text can be sent to the usercontent
frame as a string, so message cloning can add a copy. The browser-managed
Blob path does not establish a total process-memory bound.

**The main origin materializes the download Blob**, so the download affordance never lives inside the untrusted frame.

**Letterboxing is a product consequence, and it's stated here before somebody finds it in review.** The taskbar and the content sit on different origins by construction, so the content iframe is never full-viewport, and a relic authored to fill the screen renders letterboxed.

**Present the sandbox as deliberate.** An HTML relic can't navigate the top-level window, can't open popups, can't reach the decryption key, and can't reach the network: every remote source is blocked, so a page that references a CDN stylesheet, a CDN script, an external font, or a remote image renders without it. Left unexplained, the recipient concludes the relic is corrupt and the publisher concludes the product is broken, and a page stripped of its external assets makes both conclusions more likely rather than less. The taskbar says the content is sandboxed and says what that blocks, and the list it gives is the true one: top-level navigation, popups, everything same-origin, and the network itself. Publishers who need external assets must inline them.
"Can't open popups" means author code has no popup capability. A reader may
activate an absolute `http`, `https`, or `mailto` link. The frame contains
that click, validates the destination, and asks the parent to open it in a new
tab with no opener or referrer. The parent validates the destination again.
Relative, fragment-only, executable, data, blob, and local-file URLs do not
cross the boundary, and the sandbox attribute remains `allow-scripts` only.

## 5. Platform ceilings and degradation

**Secure context first.** `crypto.subtle` is restricted to secure contexts ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/subtle)), so the viewer checks `window.isSecureContext` and the presence of `crypto.subtle` before anything else and shows a specific named error. This isn't only a development concern: a recipient behind a TLS-terminating proxy that serves plain HTTP hits it in production, and a generic failure there is unresolvable by the person seeing it.

**Bounded reads.** The publication limit is 500 MiB of plaintext. The viewer
decrypts records into a browser-managed Blob and reads bounded slices for
renderers instead of allocating a whole-file plaintext buffer. Images, PDF,
audio, video, and OTIO can use the Blob path, subject to their format,
decoder, and parser limits. Download-only content retains its full bytes.

The Blob's backing storage is controlled by the browser. It may reside in
memory or on temporary disk, and OS swap may write memory to disk. Explicit
downloads write plaintext to a file. This design makes no guarantee that
plaintext stays off disk, is erased on close, or fits every device.

**Large-open confirmation.** After a mint and the authenticated record-0
envelope read, a file larger than 100 MiB presents its filename, type, and
plaintext size and asks the reader to confirm before a full-file fetch. The
initial request may transfer additional buffered bytes before cancellation.
At or below 100 MiB the confirmation is not required.

The plaintext size in record 0 is authenticated. A size derived from the
ciphertext length before authentication is an allocation guard, not an
authenticated statement about the file.

**Large text.** Code and plain text larger than 100 MiB use a windowed source
view across the whole file. Markdown, HTML, and JSX above that threshold use
the same source view rather than rendering or executing the full document.
The view reads slices, supports scrolling and line navigation, and resolves
comment targets beyond the visible window. The original truncated-prefix
choice is superseded.

**Format-specific bounds remain.** The model parser keeps its 16 MiB and
geometry limits (§3.7). OTIO ZIP archive and expanded-data limits are 500 MiB;
inflated ZIP data and the timeline document each have a separate 100 MiB
limit, and the ZIP directory is bounded at 16 MiB.

The earlier three-tier design included a future ServiceWorker streaming path.
That path is not built by this change. A root ServiceWorker used for other
viewer behavior is separate from it.

## 6. Every screen the recipient sees

### 6.1 Base load states and version-history substates

This section's first four states describe a public relic, whose key is the fragment. A private relic's URL has no fragment, so item 1 never applies to it, and a private relic is never the missing-key state. Its base states come from the server's access declaration, which the private-state paragraph below names.

1. **Missing or malformed fragment.** Split by navigation type, which is available from `PerformanceNavigationTiming` (Safari 15+, iOS 15.1+). On `reload` or a `back_forward` that re-executes, the page says the key was stripped from this URL after it opened and points back to the original link. On a fresh `navigate`, it says the link is missing its key. Both are actionable; a single generic message isn't. **When no navigation entry is available, the viewer shows the fresh-`navigate` copy.** The default is chosen, not arbitrary: telling a first-time visitor the key was stripped after their page opened describes a session they never had, while telling a reloading recipient the link is missing its key is less specific and still points at the right remedy. The fallback is the copy that's actionable either way.
2. **Unknown container version.** Refused before minting, before consuming a download cap, and before any egress, because the version marker is in the fragment (`format.md` §2.2, §3.7). A second refusal happens after the fetch when the envelope version disagrees with the marker, or when `idlen != 0`.
3. **The server refused to mint**, with the stated reason surfaced verbatim rather than flattened into "something went wrong."
4. **Decrypt failed, split at the first record.** **A record-0 failure** is a wrong key or a damaged start of the file, which are indistinguishable at the API level, so the copy names both causes and never says "wrong key" (`format.md` §3.5), and the download stops after that record (§6.4). **A failure after record 0** cannot be the key, because record 0 authenticated under it, so the page says the link is fine and the stored file was changed or damaged (§6.4), with no key entry.
5. **Success**, covered by §6.3 and §6.4.
6. **Success with no history.** When `current_version == 1`, the taskbar carries no comparison control and the page says nothing about versions. Absence is deliberate. A recipient with nothing to compare should not have to parse a disabled control or an explanation for a feature that does not apply. **This survived the move of version into the taskbar deliberately:** a version number on an artifact with no history invites a question that has no answer, and absence is still the right answer.
7. **History available.** When `current_version > 1`, the current plaintext is at or below the comparison ceiling for its class, and its renderer is diffable, the taskbar adds **Compare versions**. Version sits in the identity zone as artifact metadata, next to the catalog number. **A picker with one choice is not a picker.** At `current_version == 2` there is exactly one historical version, so the taskbar renders a **label** and the Compare versions action is the only control. At `current_version >= 3` it renders an owned in-page listbox, keyboard operable, with a visible focus state. A native `select` was replaced rather than styled: a native popup cannot be positioned or styled, and on macOS it rendered as a large box detached from its control, which reads as broken. That is a platform limit, not a CSS defect. Opening Compare versions defaults to `current_version - 1` and offers every retained earlier version. The heading and history statement always name numbers, never only relative words: **"Comparing version 2 with version 5"** and **"Version 5 is current. Version 2 is retained history and may contain content removed from the current artifact."** Changing the historical version updates both numbers before the fetch starts. While the second mint, fetch, and decrypt run, the result area says **"Loading version 2 for comparison."** Fetching the comparison consumes one additional mint, exactly like any other signed download.
8. **Markdown comparison.** **This item previously said Markdown compares source lines, not rendered prose. That is reversed.** A source-line diff of a Markdown file is a text diff of the author's typing, not a visual comparison of the page a recipient reads, and the feature exists so they can see what changed on that page. Markdown now compares **rendered prose**. It can, because it renders on the service origin through an escape-first renderer whose element and attribute set the viewer fixes, so both versions become DOM trees on that origin and are compared structurally, with no frame involved. Additions, removals, and changes carry distinct highlight outlines in the rendered prose. The mode label is **"Rendered comparison"** and the counts read **"3 added, 1 removed, 2 changed."** Whitespace-only and reflow-only source differences report no change, because they change no pixel. A recipient who reindents a document sees "no changes", and that is correct for a visual comparison and would be wrong for a source one. The plaintext and the diff result stay in the recipient's browser.
9. **Code comparison.** Code compares source lines under the mode label **"Code comparison."** For code, the source is the visual form, so the line and intra-line algorithm lives here and nowhere else. Added and removed lines carry distinct backgrounds, and a one-line replacement emphasizes changed words inside the line. It does not run either version and it does not trust a language hint to create elements or attributes outside the viewer's fixed diff vocabulary.
10. **HTML and JSX comparison.** **This item previously rejected rendered-DOM diffing**, on the grounds that it would execute two versions of author code, compare output that can depend on time and browser state, and require a second rendering protocol for a result already exact at the source layer. **That is reversed.** The requirement that changed: a source-text diff of markup is a text diff, not a visual diff, and the feature exists to let a recipient see what changed on the page. Both now compare **rendered output** under the mode label **"Rendered comparison"**. The comparison uses **two render frames**, not two renders in one frame. Each frame is network denied and each keeps its one-render-per-frame guarantee, so the invariant is preserved rather than traded. Relaxing the guard to render twice in one frame was rejected, because the guard exists to stop anything that can post to the frame swapping content after the recipient has decided to trust what they are looking at, and a second render is exactly that swap. The parent cannot read a frame's DOM, because the render frame is an opaque origin. So each frame captures its own resulting DOM as a **structured tree** of tag names, a fixed attribute allowlist, and normalised text, and posts it to the parent as `relic:tree`. **No markup crosses back to the service origin.** The parent diffs the two trees and posts `relic:annotate` to each frame. **An annotate message carries only a child-index path and a kind enum, never text and never markup.** That is what makes a second message type safe where a second render would not be: the channel is structurally incapable of changing what the document says. It is refused before a render and refused a second time. Each frame applies `data-relic-diff` attributes to the addressed elements and injects Relic's own constant highlight stylesheet, which the frame's `style-src 'unsafe-inline'` already permits. Non-rendered subtrees, `script`, `style`, `link`, `meta`, `title`, `head`, `noscript`, and `template`, are excluded from capture, because a change inside one is invisible to a reader and would inflate the count with something nobody can see. The two frames are overlaid with a swipe control, and a side-by-side layout is offered, so the recipient can flip between the two renders. The diff algorithm stays in the service-origin bundle and is absent from the frame bundle, and a build-artifact test asserts both directions. **The residual is honest:** the captured tree is what the browser actually rendered, so a page whose output depends on time or on browser state can differ between the two captures for reasons that are not a version change. The viewer does not claim otherwise, and the swipe overlay of two real renders is the primary evidence while the change list is the annotation. The source-text line diff is not gone. It is now scoped to `code`, where text is the visual form.
11. **Image comparison.** A changed raster image gets a swipe control that reveals the current version over the selected historical version. Both labels carry version numbers, the slider has the accessible name **"Reveal version 5 over version 2,"** and the summary states both dimensions and their signed delta: **"Version dimensions: 640 x 480 px to 800 x 450 px. Width +160 px, height -30 px."** This is visual comparison only. The viewer does not claim per-pixel or structural analysis. Images sit under the same 16 MiB comparison ceiling as every other comparable class. A decoded bitmap is still many times its encoded size, so a comparison near the ceiling can cost more RAM than a markdown file of the same byte length, and that is accepted so a document can compare.
12. **No changes.** Every diffable mode detects byte-identical content before rendering an empty comparison and says **"No changes. These versions have identical content."** Text modes also arrive here when decoded source strings are identical. An empty result area is never used to mean no changes.
13. **History present but comparison unavailable.** A class with no comparison mode does not get a broken control: the taskbar offers **Earlier versions**, which opens a chosen version on its own. Media, OpenTimelineIO and PDF relics play or render in the browser and nothing on their page offers a comparison, so the current page carries no comparison notice; opening an earlier version says why it is alone, in that class's words, for example **"Relik cannot show version 1 of this timeline beside version 2. It is open here on its own."** A download-only relic keeps its notice on the current page: **"This file is download-only, so Relik cannot show two versions side by side in the browser. Each version can still be opened on its own."** A current plaintext above the ceiling also keeps rendering normally, under **"This version is larger than the 16 MiB comparison limit, so Relik cannot show it beside another. Earlier versions can still be opened on their own."** for every comparable class. An earlier version shown on its own carries its own reason and never the current page's notice as well. A historical version above the ceiling is refused after its mint and before its ciphertext fetch, naming that version and confirming the current version remains open. Other historical fetch or decrypt failures stay inside the comparison panel.

**The comparison ceiling is 16 MiB per version.** It is separate from the
500 MiB publication cap and the 100 MiB threshold for windowed source.
Versions too large to compare can still be opened individually.

**Version history does not change the trust boundary.** The viewer mints each selected ciphertext through the existing service path, decrypts both versions with the one fragment key, and computes the result client-side. No plaintext and no diff result reaches the service. **An earlier version of this paragraph said the frame receives neither historical source nor diff output, and that no comparison message type is added to its `postMessage` protocol. Both of those are reversed.** Each frame receives only its own version's payload. Two comparison message types exist, `relic:tree` and `relic:annotate`, and they are safe because of what they cannot carry: the tree is tags, an attribute allowlist, and normalised text, never markup, and the annotate channel carries no content. The diff runs client side, in the service-origin bundle.

**For a private relic this paragraph changes in one place.** A private relic has no fragment and so no single fragment key. Each selected version is decrypted with that version's own content key, obtained through `keyFor(version)` (plan 4.15), and each version the reader opens is verified first, as 6.12 describes. The sentence above is the public-relic rule.

**Transport integrity and authenticity are distinct.** CRC32C, when checked,
can detect transport corruption but is not an authenticity proof. Each
encrypted record has an AEAD tag, and a later tag or length failure must not
be presented as a wrong-key failure after record 0 has authenticated. The
former tier-specific CRC ordering described a whole-buffer and a
ServiceWorker download design that this change supersedes.

**Private base states come from the access declaration.** A private relic's shell root carries `data-relic-access="private"`, and its host `#relic-private[data-private-state]` takes one of `signin`, `setup`, `setup-refused`, `replace-offer`, `request`, `requested`, `declined`, `unlock`, `ready`, `revoked`, `denied`, `owner-changed` or `seal-mismatch`. Section 6.12 says what the reader does in each state and quotes the copy the plan fixes. The plan does not map each state from the declaration, which 6.12 lists as an open item.

### 6.2 The unfurl card

The fragment never reaches a server, so no unfurler can describe the content, and **a blank card on an unfamiliar domain is the visual shape of a phishing link.**

**A private relic's card is the generic private card.** `GET /{id}` for a private relic serves `data-relic-access="private"` on the root, also when the relic has expired. Its card is generic: title `Relic`, description "A private relic. Sign in to open it.", no cover, no title, and no renderer-class copy (plan 4.7, 4.13). The per-relic tags above do not apply to it, and it carries the constant fallback image.

`/{id}` serves deliberate Open Graph and Twitter Card metadata describing what Relic is and revealing what kind of thing the link holds, without pretending to describe the encrypted payload. Open Graph's required properties are `og:title`, `og:type`, `og:image`, and `og:url`, with `og:description` and `og:site_name` optional ([Open Graph](https://ogp.me/)).

**What stays constant and what becomes per-relic.**

- **Per-relic tags:** `og:title`, `og:description`, `twitter:title`, `twitter:description`, `og:url`, and (when a cover image is uploaded) `og:image`, `twitter:image`, `og:image:type`, and `og:image:alt`. `og:url` is `{serviceOrigin}/{id}` when the path segment is a valid relic id, or the service origin root otherwise.
- **Constant tags:** `og:type` (`website`), `og:site_name` (`Relic`), `twitter:card` (`summary_large_image`), and the fallback `og:image` path `{serviceOrigin}/assets/card.v1.png` (a 1200x630 PNG with `og:image:type` of `image/png`, `og:image:width` of `1200`, `og:image:height` of `630`, and `og:image:alt` of "Relic's accession label with an empty field stack: a relic's catalog number, an unrevealed key line, and a prompt to open with the full link.").

**Cover image tags on the unfurl card.** On 2026-10-13, per-relic cover images were introduced, reversing the one-constant-raster invariant. When a relic has an active cover image matching the current version (`row.cover?.version === row.version`):

- `og:image` and `twitter:image`: `${serviceOrigin}/${canonicalId}/cover/${cover.sha256}.${coverExtension(cover.type)}`
- `og:image:type`: `cover.type` (`image/png` or `image/jpeg`)
- `og:image:width`: `1200`
- `og:image:height`: `630`
- `og:image:alt`: `COVER_ALT[cover.kind]` (e.g. "The opening of this Markdown document, as it renders.")

When a relic has no cover, when `cover: false` was passed, or when the relic is expired, tombstoned, unknown, or a store read throws, `og:image` falls back to `{serviceOrigin}/assets/card.v1.png` with the constant fallback tags.

**`og:description` and `twitter:description` reveal the coarse renderer class.** The description combines a phrase naming the kind of thing with a tail selected by what the viewer actually does (`CLASS_BEHAVIOUR` from `@relic/format`), not by `isRenderable`. `isRenderable` is the success metric's wedge boundary and excludes `media` because the telemetry counts only the document and markup wedge. Using `isRenderable` previously produced a false recipient-facing statement claiming that media files download to the device, whereas the viewer routes `media` to an in-browser player. The three tails map to the viewer's three actual outcomes:

- Class phrase:
  - `markdown`: `A Markdown document.`
  - `code`: `A source code file.`
  - `html`: `An HTML page.`
  - `jsx`: `A JSX component.`
  - `image`: `An image.`
  - `pdf`: `A PDF document.`
  - `model`: `A 3D model.`
  - `media`: `An audio or video file.`
  - `archive`: `An archive.`
  - `binary`: `A binary file.`
  - `otio`: `An OpenTimelineIO timeline.`
- Tail:
  - Renderable tail (`renders`: `markdown`, `code`, `html`, `jsx`, `image`, `pdf`, `model`): `It opens in your browser, and only someone holding the whole link, including the part after the #, can open it.`
  - Playable tail (`plays`: `media`, `otio`): `It plays in your browser, and only someone holding the whole link, including the part after the #, can open it.`
  - Download-only tail (`downloads`: `archive`, `binary`): `It downloads to your device, and only someone holding the whole link, including the part after the #, can open it.`
The description tag value is the class phrase, one space, and the matching tail (for example, "An audio or video file. It plays in your browser, and only someone holding the whole link, including the part after the #, can open it.").

**`og:title` and document `<title>` carry the title or a per-class fallback.** When titled, `og:title` and `twitter:title` are the publisher-declared plaintext title, and the document `<title>` is `{title} · Relic` (using a U+00B7 middle dot, never a dash). When untitled, the title falls back to a per-class label:
- `markdown`: `A Markdown relic`
- `code`: `A code relic`
- `html`: `An HTML relic`
- `jsx`: `A JSX relic`
- `image`: `An image relic`
- `pdf`: `A PDF relic`
- `model`: `A 3D model relic`
- `media`: `A media relic`
- `archive`: `An archive relic`
- `binary`: `A binary relic`
- `otio`: `An OpenTimelineIO relic`
For an untitled relic, `<title>` is `{Class} relic · Relic` (for example, `A Markdown relic · Relic`), while `og:title` and `twitter:title` carry the per-class fallback string verbatim.

**Declining a title does not hide the class.** The title is publisher-declared and declinable: a publisher can pass an empty title or clear it on republish. The class is derived from the bytes by the publishing client and is not declinable.

**Tombstones, expiry, read errors, and malformed identifiers.** The class is gated on the exact same liveness check as the title. A relic that is tombstoned, expired, unknown, or whose id is malformed, or whose store read throws, serves neither the stored title nor the class metadata; it serves the constant fallback card:
- `og:title` and `twitter:title`: `A relic`
- Document `<title>`: `Relic`
- `og:description` and `twitter:description`: `An encrypted file. It opens in your browser, and only someone holding the whole link, including the part after the #, can read it.`

A takedown removes the title and stops serving the class alongside the rest of the relic record. A store read failure still serves the shell with the fallback card, never a 500. Titles are attacker-influenced display text: they are escaped with `escapeHtml` on every emission, including inside attribute values.

**Serving that metadata must not mint**, or every unfurl burns a download cap and counts as an open.

**There is no conflict with the noindex precondition, and this gets said out loud so nobody removes the tags in that rule's name.** Open Graph tags are consumed by unfurlers rather than indexers, and Slack documents that it ignores `robots.txt` outright: "We do not currently honor `robots.txt` files. After implementing and experimenting with doing so, we received too many complaints from our users because a great portion of the Internet is inaccessible to crawlers" ([Slack](https://api.slack.com/robots)). A `robots.txt` disallow was never going to stop the unfurl, so deleting the metadata would produce the blank phishing-shaped card and buy nothing.

### 6.3 Before decryption completes

Everything except the content renders immediately: the branded taskbar, the service name, one line of plain-language explanation of what Relic is and what's about to happen, the abuse-report link, and the privacy-statement link (`spec-service-surface` owns that statement's contents). The recipient is deciding whether to trust an unfamiliar domain during exactly this window, and an empty page spends it badly.

**The honesty constraint applies hardest here.** "Nobody can read this but you" is an overclaim on the one surface where it does the most damage. The decryption JavaScript is served by the same operator the claim is made against, so it's a claim about operator intent rather than a property a recipient can verify. The copy says what's true: the key stays in the link and this browser, and the recipient's browser never sends it to Relic's servers. For content that renders on the usercontent origin, the viewer carries a compact marker in the header chrome stating that the page runs the author's code, linked to `/policy` where the full isolation guarantees and limits are stated.

**Private relics.** The key line above describes a public relic. A private relic's link carries no key, so that line does not apply to it. Everything else in this list still renders. The state shown in place of decrypted content comes from the access declaration (6.1, 6.12), and its copy never names a title, because a private relic has none (plan 4.13).

### 6.4 Progress, input, and errors

**Progress identifies fetching, decryption, and rendering.** Fetching uses the
mint response's ciphertext object length for its total; decryption uses
authenticated record progress. Fetch and decryption can overlap.

**Key entry appears only after an open has failed.** This paragraph banned any key-entry field on the viewing origin, not configurable and not conditional, as a purpose-built phishing surface aimed at the system's only secret. A field shipped anyway on the missing-key and could-not-be-opened screens, and on 2026-10-24 Jason Waldrip chose a Copy link panel whose keyless link works only because the recipient types the key phrase there, so the ban is amended to the field as it ships. It never appears on a page that opened. It accepts the key phrase or the full link, nothing typed into it leaves the browser, and it is never offered unprompted. The phishing concern stands, and it is the reason for each of those limits.

**Every error screen is a relic page**, carrying the abuse-report and policy links. An error state is where a recipient most wants to report something, and it's the state most likely to be reached by somebody who was sent something they didn't want.

**The copy-link affordance.** `format.md` §2.5 strips the fragment via `history.replaceState`, which is honored here, and both costs land on this document. The recipient can no longer re-share from the address bar, so **the viewer carries an explicit copy-link control, present from load, backed by the in-memory key** and reconstructing the full URL on demand. Pressing it opens a small panel under the taskbar instead of copying straight away. The panel shows the full link with Copy link, a Copy without the key that copies the link with its fragment removed, and the 12-word key phrase for the same key with its own Copy, so a reader can send the link without the key and say the phrase separately; the recipient types the phrase where the keyless link's page asks for the key. The phrase is computed in the browser when the panel opens, from the key already in memory, through a lazily loaded module that keeps the wordlist out of the shell. It exists only in the open panel: it is never written to storage, the address bar, a title, a toast, a log, or a request, and closing the panel removes it from the page. Escape and the close button return focus to Copy link. Below 34rem the control is icon-only and keeps its accessible name. The reloaded page is dead and says so per §6.1 rather than showing a decrypt error. Present stripping as shrinking the window rather than closing it: the URL with its fragment existed before the replace, so browser history sync, an extension with host permissions reading `window.location.href` at load, and the application the link was clicked from all still saw it.

**For a private relic the copy-link control copies the keyless URL only.** The panel above does not apply to it: a private relic offers no Copy without the key, no key phrase and no key-bearing link (plan 4.13). Its keys are held by the reader's passkey, not by this tab (6.12).

**Repeat opens reuse a still-valid signed URL rather than minting per page load**, keyed by relic ID, with validity judged against the expiry the mint response carries. A restored tab, a pull-to-refresh, and a back-forward navigation are each otherwise another mint and another counted open. A bfcache restore needs no handling, since the page resumes with its in-memory key intact.

**The first record is the key check.** Record 0 carries the envelope and authenticates on its own, so the viewer reads the signed download as a stream, decrypts record 0 as soon as its bytes arrive, and cancels the download when its tag fails. A link whose key does not open the relic costs one block of egress instead of the whole object. The could-not-be-opened screen keeps that block, so a key typed there is checked locally before anything is fetched again. The check runs only in the browser: no key, proof, or verifier is sent for it. The one new observable, an open that stops after its first block, is disclosed (`service.md` §5 item 10).

**After record 0, a failure is the file's, not the link's.** Once record 0 authenticates, the key is proven. A later record that fails its tag, a container without its final record, bytes after the final record, or content that disagrees with the envelope's length shows: **"The start of the file decrypted with this link, so the link is fine. A later part did not, which means the stored file was changed or damaged."** It offers Try again and Report this relic, and no key entry, because no other key would help. A transfer that ends short of the mint's object length is a network failure and says so. Try again reruns the open with the key still in memory; reloading would land on a page whose key was stripped.

**The PWA case is two cases, and only one is the neutral page.** A cold launch from the home screen loads the manifest's `start_url`, which holds no relic and no key, so it lands on the landing page (§6.7). Originally, that page explained what Relic is and held nothing until a link was opened, matching the old non-goal ruling out a dashboard and a "my relics" list. From 2026-10-06 to 2026-11-05 it listed the relics this browser had opened. As of 2026-11-05 it is the introduction again, and its header carries one link, "Your relics", to `/dashboard`, where the browser's relics are listed. A cold launch therefore shows the introduction and never reads the key vault. **A warm relaunch that resumes an already-running instance doesn't navigate to `start_url` at all**, so the recipient lands back on the live relic with the key still in memory, which is the opposite of the neutral page and the more common case on mobile. Even the cold path is advisory: the manifest spec says the `start_url` member "is purely advisory, and a user agent MAY ignore it or provide the end-user the choice not to make use of it" ([W3C appmanifest](https://www.w3.org/TR/appmanifest/)). **So no key-hygiene rule rests on `start_url`.** The ones that hold are §1.8 and the `history.replaceState` strip, and neither depends on the manifest.

### 6.5 The taskbar's element accounting

Version moved into the taskbar, then Comments did, and the row had already overflowed once at narrow width before either arrived. The accounting is the control, so a future addition has to displace something named.

**Three zones, left to right, each separated by a hairline rule.**

1. **The wordmark zone.** One element: `relik.link`. The domain rather than a product name, because the recipient is deciding whether to trust an unfamiliar address bar.
2. **The identity zone.** Four elements: the filename, the relic id, the version control, and the zone itself as the only flexible column on the row. Version joins this zone because a version number is artifact metadata of exactly the same kind as the catalog number beside it, and because the identity zone is the one that already absorbs pressure through an ellipsis. Putting a fixed-width control in the actions zone instead would push a control off the row.
3. **The actions zone.** Seven elements: the isolation marker, Comments, Decisions, Compare versions, Copy link, Download, Report. Comments carries a count and is conditional on the relic being renderable. Decisions carries a tally of approvals and rejections, opening the decision panel on renderable relics. Compare versions is conditional on history being present and diffable.

**Twelve elements at the widest.** Eleven when a relic has history that cannot be compared, because the version control stays and Compare versions goes. Ten when `current_version == 1`, because both go and §6.1 item 6 says nothing about versions at all. Eleven on a download-only relic, which gets no thread and no decisions for the same reason §6.1 item 13 gives it no comparison control: nothing rendered, so there is nothing on the page to comment or decide about. It was eleven at the widest before Decisions arrived, ten before Comments arrived, and nine before version did.
**Comments went into the actions zone rather than beside version, and the version precedent is what settles it.** A comment count looks like artifact metadata and is not: it changes while the reader is on the page, it is a place to go rather than a fact about the file, and the identity zone's flexibility is the ellipsis on the filename, which a count cannot use. What it does share with version is that it must not push a control off the row, and at every width above the floor it does not.

**The narrow hierarchy is re-derived at a 320 CSS pixel floor.**

- Below 34rem, every action collapses to its icon. That already shipped, and the comment in the stylesheet records why the isolation marker collapses with them rather than keeping its label: exempting it pushed Report off the row at 420px.
- Below 34rem, **the count survives the collapse that hides the label beside it.** It is two characters, and it is the whole point of the control: a bare speech bubble says a thread might exist, while `2` says what is in it. A reader cannot get that number anywhere else on the row.
- Below 34rem, **the wordmark is also hidden.** At 320px the actions need about 11.9rem of the available 20rem and the version control needs about 3rem, which leaves nothing for a 6.7rem wordmark and a filename both. The wordmark is the least load bearing element on the row at that width, because the domain is in the address bar directly above it, while the filename, the version, and the four actions are not available anywhere else. Brand gives way before function.
- The version control collapses its own label from `Version 5 of 5` to `v5/5` at the same breakpoint.
- **Below 24rem, Comments and Decisions leave the row.** Measured in Chrome against a live instance, on a relic at `current_version == 3` so the version control is present. At a 320px viewport, where a classic scrollbar left the row 305px, the five collapsed actions take 195px, the version control 56px, and the filename keeps 88px. Forcing additional controls back on takes the actions over available width and collapses the filename to an ellipsis and about two characters. The row does not overflow, it eats the filename, because the identity zone is the flexible column and the filename is what flexes. That is worse than an overflow, not better: an overflow is visible and a silently truncated name is not. Below 24rem, the decision stamp and Comments control leave the taskbar. Decisions remains accessible through the stage bar or secondary popover and panel.

**Comments and Decisions are the elements that leave the row because the layout below the taskbar carries secondary access to them.** A persistent vertical Comments tab sits on the right edge of the stage row, reachable at every supported width, so below 24rem it becomes the entry point when the taskbar Comments control is absent. Every other candidate on the row leads somewhere reachable only through it: the isolation marker is the one place the author-code disclosure appears since §6.3 demoted the banner, and Compare versions is the only entry to comparison on a relic at `current_version == 2`, where the version control is a label rather than a picker. Losing either would cost a reader something the page does not otherwise say.

**What must never be lost at 320px: the filename, the version, Copy link, Download, and Report.** That is the floor's completion criterion, and it is unchanged. Neither Comments nor Decisions is on it. A future addition has to displace something named rather than overflow the row, and the remaining candidates both have the price above attached to them.

### 6.6 The comment thread

`frame.md` reversed the no-identity non-goal and the reversal is what makes this section possible: accounts exist in exactly one form, a verified email address per commenter, and, for public relics, the address is the identity. It reversed nothing else at the time. (A separate `/dashboard` route was later added for key backup and listing opened and commented relics. On 2026-10-06 Jason Waldrip authorised rendering the browser's opened relics list on the homepage `/` as well, and on 2026-11-05 that list became a header link to `/dashboard`. Until 2026-11-11, nothing in either reversal granted sharing groups, team features, or server-side access permissions. On 2026-11-11 private shares changed that for private relics only: a passkey-bound identity holding a wrap for a version may read, comment on and decide that version (6.12). Public relics keep the address-only rule, and no sharing groups or team features were added.)

**The thread is in the service-origin chrome and it is not negotiable which side it sits on.** The render frame is network denied, `default-src 'none'` with sandbox exactly `allow-scripts`, so it could not fetch a comment if it tried. The chrome around it can, and it is also the only side of the boundary holding the key the bodies are sealed under.

**The thread is a right sidebar beside the relic, and this section's earlier posture is reversed.** The thread previously sat in a bottom panel pinned inside `.stage-wrap`, absolutely positioned above the rendered relic so that opening it left the relic's layout untouched. That is reversed, and the reason is the product's own: reading and commenting happen together, so the conversation sits beside the artifact rather than after it. A reader who wants the thread should not have to finish, or dig past, the reading surface to find it. The body is a column, the taskbar on top and one row below it; the row holds `.stage-wrap`, the rendered relic, and an `aside.thread` sidebar on the right. `.stage-wrap` flexes to fill whatever width the sidebar does not take, it is the scroll container, and marks and pin targets are painted inside it, so they reflow with the relic when the sidebar opens or closes. Nothing sits below the content. The relic is never covered and never pushed down; opening the thread narrows it, and that is the whole of the interaction between the two.

**Closed by default, and closed occupies no width.** The row then holds `.stage-wrap` alone at full width, plus a persistent vertical **Comments** tab on the right edge. The tab exists at every viewport width, so the thread always has an entry even where the taskbar's Comments control has left the row (§6.5), and below 24rem it is the only entry. The taskbar Comments control and the edge tab both toggle the sidebar. Aiming a comment at the relic does not open it: a verified reader writes that comment in a panel attached to its target on the stage, and only a reader who still has to verify an address is taken to the sidebar, because the address is verified there. While open, a drag handle on the sidebar's left edge resizes it: the width is clamped from both sides, never narrower than a usable thread column and never so wide that the relic's reading column stops being usable, and the chosen width persists across loads. The storage rule at §1.8 binds the fragment and the key, not a layout preference. Closing the sidebar hides the thread, never the annotations: marks and pin targets remain painted in `.stage-wrap`.

**Below 44rem the sidebar takes the row and the relic is hidden.** Side-by-side reading is impossible there: the narrowest readable thread column and a readable relic column do not both fit, and keeping the relic technically visible would mean shrinking it to a column nobody can read, which trades the reading surface away for a technicality. So below 44rem an open sidebar occupies the full row width and the relic is hidden while the thread is open; closing the thread brings the relic back at full width. **This is not the taskbar's 24rem floor and the two must not be conflated.** That number is the row's own arithmetic for six controls (§6.5); this one is the width where two readable columns stop fitting, and it is the wider of the two. The taskbar sits above the row and is unaffected, so the 320px must-survive list in §6.5 still holds.

**Marks are carried across every renderable surface, and the distinction is the surface rather than a blanket frame boundary.** Marks are painted in the viewing origin's own DOM or delegated across the frame bridge. A text mark is painted by `wrapTextQuote`, which walks text nodes under a host element and wraps the first exact occurrence of the quote in a `mark` element (`packages/relic-viewer/src/comments.ts`), called from `paintMarks` inside `buildThread` (`packages/relic-viewer/src/main.ts`). That host is `.stage-wrap`, the element `buildThread`'s `attach` is handed by `renderReady` and built by `buildStageWrap`. A pin is the point shape: `paintMarks` builds a button inside a `div.comment-pins` overlay appended to that same host and places it by fraction of the host's scroll box through `pinOffsets`. Precise kinds delegate to registered adapters (`packages/relic-viewer/src/anchor-adapters.ts`), which paint regions on images, timecodes on media tracks, and page rectangles on PDFs. **Every citation in this block names a symbol first and gives its line second.** The name is the identifier and the number is the convenience.

**Annotation announces itself, and a target the reader cannot see is treated as a correctness problem rather than a rough edge.** A pending target that is invisible does not merely fail to help: a stray selection made while reading silently anchors the next comment to the wrong line, and neither the writer nor the reader ever learns it happened. So three things are settled. **A selection raises the selection offer** (`.popover-offer`), placed above the live selection inside the stage and offered only for a selection that is not collapsed, is inside the stage, and is non-empty after trimming. It offers **Copy text** and **Comment**, with a way to decline both. **Comment** opens the stage composer on the selection for a verified reader; for a reader without a verified address it locks the quote as the sidebar composer's target, opens the thread, and puts focus there. The offer is dismissed when the selection collapses or Escape is pressed. **The sidebar composer always carries `.compose-target`**, from load and before any selection exists, reading "Commenting on the whole document" with no target, `Commenting on "<quote>"` for a text target with the quote truncated for display, or "Commenting on a point" for a pin, the last two carrying a `.compose-target-clear` control labelled **"Clear"** that returns to the whole document. **The chip is present in the no-target state deliberately**, because that is what makes anchoring discoverable to somebody who has not selected anything yet, and because it puts the target in front of the reader in the moment before they post rather than after. The stage composer names its target in its own `.popover-target` line and leaves the sidebar chip as it was.

**`walkContentTextNodes` is the one text flow both capture and resolution read, and a mark's text is part of it.** The flow is every text node under the host except overlays and controls this page added (`.comment-pins`, `.comment-region`, `.mark-bubble`, `.mark-hint`, `.mark-quote-action`), `script`, `style`, anything carrying `hidden`, and `pre.raw` (`packages/relic-viewer/src/comments.ts`). Two exclusions are load-bearing and one earlier exclusion is now a defect. `pre.raw` is the Markdown source `renderMarkdownView` keeps beside the rendered prose for the source toggle: in the flow it puts the whole document in twice, so every phrase gains a second candidate and a quote at the end of the prose takes its trailing context from source the reader cannot see. **`mark.relic-text-mark` used to be excluded and is not any more.** Capture runs with marks on the page and resolution runs immediately after `unwrapTextQuotes` has removed them, so excluding them gave the two ends different documents: a reader who had already commented and then selected text inside their own mark produced a selection whose container was absent from capture's flow entirely, and the capture fell back to the first occurrence it could still see. The stored anchor then described a place in another paragraph, beside the earlier comment. The chip named the reader's words either way, so the only surface that showed it was the mark.

**`captureSelectionQuote` returns no anchor rather than an invented one, and `offer` withholds the bubble when it does.** The fallback that wrote `{kind: "quote", exact}` for a selection it could not locate is gone from both the capture and its call site in `main.ts`. An anchor pointing somewhere the reader did not select cannot be seen to be wrong until after they post, which makes it worse than no anchor; a bubble that would produce one is not offered. With the flow fixed this is unreachable for an ordinary selection on the stage, and `annotate-quote.test.ts` asserts that a selection inside an existing mark captures the position the reader chose.

**Overlap paints and nesting cannot accumulate.** Two comments on the same words is ordinary, and `wrapTextQuoteWithContext` no longer drops the second: a dropped mark tells a reader their comment points at something the page cannot show while the text sits in front of them. Repaint cannot pile marks up, because `paintMarks` calls `unwrapTextQuotes` before it paints, so the only marks present during a pass are the ones that pass put there. The provisional target stays legible where it lands on top of a posted mark: `.relic-text-mark.is-pending` is heavier than a posted mark rather than lighter, and carries a dashed border and dashed outline where `.is-active` is solid, so the difference from both is one of kind and not only of degree.

**On `html` and `jsx` the content sits behind a cross-origin frame, so the parent cannot reach into its DOM directly.** `renderSandboxedHtml` and `renderSandboxedJsx` each wrap exactly one iframe (`main.ts` 762 to 775 and 782 to 806), built by `sandboxFrame` (`main.ts` 688 to 733), which sets `sandbox="allow-scripts"` with no `allow-same-origin` and points `src` at `${usercontentOrigin}/sandbox.html` (696 and 698). That document is opaque origin, so the `TreeWalker` inside `wrapTextQuote` does not enter it (`comments.ts` 659), and the subtree the parent can walk is a `div.doc.doc-html` or `div.doc.doc-jsx` holding a single iframe element with no text node in it. Nor does a reader's act inside the frame arrive on this side by itself: a selection there is not this origin's `window.getSelection()` to read, and a click there is delivered to that document rather than to the `mouseup` and `click` listeners `attach` binds on the host (`main.ts` 2303 to 2332).

**What is missing is a message type, not a channel, and the distinction decides whether this is a boundary or a law.** A bidirectional `postMessage` channel between the parent and the frame is already in place and already carries DOM data. `sandboxFrame` posts inward through its `post` helper (`main.ts`) and listens through its `onMessage` handler; on the other side, the shim's `reportTree` posts `{ type: 'relic:tree', tree: captureTree(document.body) }` outward and its boot block announces `relic:sandbox-ready`. Forwarding a selection outward (`relic:frame-selection`), reporting a clicked point (`relic:frame-point`) or dragged box (`relic:frame-region`), and accepting arming (`relic:arm-pointing`) or mark painting (`relic:paint-mark`) inward, bridges the boundary over typed messages rather than relaxing the origin separation. The frame tells the parent what was selected or aimed, and the parent instructs the frame where to place its marks.

**The frame reports geometry, and the page draws the popover.** Hovering and activating an existing mark inside the frame must show the parent its own controls, and the page's UI cannot read the frame's DOM, so the frame sends where the thing is rather than the parent reaching in. `annotate-frame.ts` owns the message vocabulary: `FrameSelectionMessage` (`relic:frame-selection`, carrying a `rect` plus the selected text and a `truncated` flag because the selection text is capped at `FRAME_SELECTION_TEXT_LIMIT_BYTES` and handing back more than was stored would be a lie about what the reader selected), `FrameSelectionClearedMessage`, `FrameMarkClickMessage`, `FrameMarkHoverMessage`, `FrameMarkRectMessage` (`relic:frame-mark-rect`, one mark's geometry, sent in answer to `ActiveMarkMessage` and to the inward `TrackMarkMessage` (`relic:track-mark`), and sent again after every scroll, resize or repaint inside the frame until the page stops asking), and inward `ActiveMarkMessage` and `TrackMarkMessage`. A placed point and a drawn box also carry their own `box` in viewport coordinates on `relic:frame-point` and `relic:frame-region`, so the stage composer opens beside them before the frame has painted the provisional mark. The answer to `ActiveMarkMessage` is never a `relic:frame-mark-click`: geometry the page asked for is not a reader's press. Rects travel as `FrameRect` validated by `isFrameRect` against `FRAME_RECT_LIMIT_PX`, in viewport coordinates, because geometry left behind after a repaint is just another stale anchor. **Comment plaintext never crosses into the usercontent origin.** The frame carries geometry and never plaintext: a comment's body is decrypted and read on the viewing origin, and a popover for a mark is positioned from the message's rect rather than from the frame's own words. The popover's visual design is not settled and is not fixed here; what is fixed is that a selection popover offers `Copy text` and `Comment`, with a way to decline both. The same shape extends to the other anchored kinds: an image region, a video timecode, and a PDF page report where they are and never what they say.

**Anchored comments against framed content are displayed through this bridge.** Framed content means an `html` relic, or a `jsx` relic that actually renders as a component rather than falling back to source. The anchor rides in the comment plaintext, decrypted in `openEntry` (`comments.ts`), and `paintMarks` delegates to the registered adapters for the surface. When `iframe.usercontent-frame` is present, `frameQuoteAdapter`, `frameRegionAdapter` and `framePinAdapter` post `{ type: 'relic:paint-mark' }` into the frame. The frame shim wraps quotes with `mark.relic-text-mark` using `splitText` and DOM node manipulation (never `innerHTML`), positions region boxes on an overlay matching the frame's scrolling document box, and draws pins on the same overlay at a fixed size in pixels, because a point sized as a share of a long document is a strip hundreds of pixels tall. While pointing is armed, the frame decides click or drag in its own pixels (`FRAME_DRAG_MIN_PX`), never as a share of the document, does not start a text selection, and draws the box live while dragging. A click places a `pin`; a region stored by earlier builds as a `0.03` by `0.03` box is drawn as the point it was. Activating a comment row sends `{ type: 'relic:reveal-mark' }` to scroll the frame directly to the target, and opens that comment's card over the mark once the frame reports where it landed.

**The tools row adapts to the artifact and never makes promises it cannot keep.** The row directly under the thread title (`.thread-tools`) offers only the controls and discoverability hints that function on the active surface. Text surfaces (Markdown, Code) carry `Point at something` plus a discoverability hint `Select text in document to quote`. Selecting text raises the selection offer over the selection and reveals a keyboard-reachable `Quote selection` button in `.thread-tools`, which aims the sidebar composer. Images carry `Mark a region or point` without text hints: arming activates crosshair drawing for mouse and touch, and initializes a keyboard-aimed region box navigable via Arrow keys and Shift+Arrows, locked with Enter or Space. Touch scrolling remains natural without accidental mark placement because arming is explicit. Media relics carry `Comment on this frame` for video and `Comment on this moment` for audio, supporting span selection; media relics omit spatial rectangles (`rect`) on time anchors and omit text selection hints, while audio relics omit point toggles. PDF relics offer `Mark on page` with page-area dragging and text selection. Framed content (HTML, JSX) offers `Point at something` and `Select text inside document to quote`, bridging events over `postMessage`. Download-only relics build no thread at all. The tools that arm a gesture only arm it: the point, the region or the page box is made on the stage, so its comment is written on the stage. `Quote selection`, `Comment on this frame` and `Comment on this moment` set the target from the sidebar, so they aim the sidebar composer.

**Pin mode and region mode are armed explicitly, and the armed state is visible in three places at once.** An ordinary reading click or touch scroll must never place a mark, so the toggle is the whole gate: `.mark-mode` sits in `.thread-tools`, and its `aria-pressed` attribute is the armed state rather than a hidden class. While armed, the stage carries `is-pinning`, the cursor is a crosshair, and a live hint explains what to do. On images, `MARK_REGION_HINT` explains that clicking places a point, dragging selects a region, and arrows plus Enter provide keyboard control. A click while armed places the mark and disarms; Escape cancels active aiming without clearing previously locked targets.

**Re-aiming and target dropping preserve typed composer text.** A reader who has typed a draft in the composer and needs to move their mark can re-arm, drag a new region, select another quote, or seek to a different frame. The composer's draft text is never destroyed during re-aiming. When aiming is active, Escape cancels the aiming gesture without dropping a previously locked target. When aiming is idle, Escape or the "Clear" button on `.compose-target` drops the target back to the whole document, keeping the draft text intact in the composer.

**The test is the presence of each surface, never an assumed class, and that distinction is load bearing.** The controls are gated on inspecting what actually rendered inside the attached stage (`anchorSurfaceFor` in `main.ts`). Gating on `view.route` alone would fail when a component falls back to source view: a `jsx` relic whose bytes do not compile falls back to `renderCodeView`, and text quote controls work on that source exactly as they do on a `code` relic. A class-shaped rule would take controls away from a reader looking at selectable text. A rule stated in terms of what is actually on the page cannot drift from what is actually on the page.

**Class by class, which anchor kinds exist today.** `markdown` and `code` render inline DOM text and carry `quote` and `pin` kinds. `image` renders `img.relic-image` and carries `region` and `pin` kinds. `media` renders video or audio players and carries `time` anchors (moments and spans, omitting spatial rectangles). `sandboxed-html` and `sandboxed-jsx` carry `quote`, `region` and `pin` anchors through the sandboxed frame bridge, and `sandboxed-jsx` compile-failure fallback carries `quote` and `pin` as inline code. `pdf` renders canvas pages and carries `page` anchors. Download-only relics build no thread at all.

**A comment on the timeline is written in a popover over the scrubber, and fullscreen is kept while it is.** Every gesture that starts a time comment opens the same popover composer a text selection opens (`openComposer`, `inlineComposer`, `postComment`): the hover comment button, `c` or Enter on the focused scrubber, and a press-drag span on release. The player's `relic:time-aim` event carries a `measure` function for where the moment or span sits on the scrubber (`TimeAimDetail` in `media-player.ts`), and the panel is centred on it, below the scrubber by preference and above it when below does not fit, because the picture under review sits above the scrubber. The target line names the timecode, and the span's end when there is one. Dragging the span's end handle, or drawing a new span while the panel holds text, moves the target and the panel and keeps the text and the field. A reader without a verified address is handed to the sidebar as before, because the address is verified there. In stage fullscreen the panel mounts inside the fullscreen `.media-stage` (`popoverLayer` translates the anchor into it), the controls stay awake while it is open, and the viewer does not leave fullscreen; this reverses the earlier rule that a comment action left fullscreen before the composer opened. The one exception is the reader the sidebar has to take, who is brought out of fullscreen first, as is a press on "Open in thread". A stage going into or out of fullscreen carries an open panel with it, text and focus intact. iOS native fullscreen shows the platform's own player and none of this page's chrome, so none of it applies there.

**A timeline marker opens the same card every other mark does.** Hovering a marker opens its card after `MARK_HOVER_OPEN_MS`, and a press or keyboard focus pins it while the press still seeks to the moment and pauses. Enter on a focused marker moves focus into the card. Reply, edit, resolve and "Open in thread" work from it. A cluster opens a card listing every member, with its time to the tenth, its author and the start of what it says, and each row opens that member's own card and seeks to its moment. The bespoke `.timeline-marker-tooltip` is gone: one form per idea. A card never replaces a panel holding unposted text, and focus moving inside an open card never rebuilds it.

**Saved comment overlays can be dismissed without changing the comment.** Every saved card, including the card shown after Post and a timeline cluster's member list, offers a native **Dismiss** button (`.popover-dismiss`, accessible name `Dismiss comment overlay`). Dismiss closes only the overlay: it does not delete, resolve, send a request, open the sidebar, change counts, seek, stop playback or leave fullscreen. The comment remains available from its mark and thread, and the mark can reopen its card. There is no automatic dismissal. New and edit composers do not offer Dismiss, and the button is hidden while replying so it cannot discard a reply draft. Keyboard dismissal restores focus without reopening the mark during that synchronous focus restoration. Work started by a dismissed saved card must not reopen it or overwrite a newer panel.

**Images inside HTML have their own attached comments.** Each eligible image gets a shim-owned native **Comment on image** button usable by pointer, touch and keyboard. Ordinary image clicks, including linked-image navigation, keep their existing behavior. Activating the button opens the existing composer directly, reading **Commenting on an image.** An unverified reader follows sidebar verification with the target retained. New-comment controls and saved badges are separate; multiple comments remain individually reachable. Dismiss leaves the comment, badge and thread intact.

The sealed anchor is `{kind:'image', path:[{tag,index}], source_sha256}`. Its revision-local path starts at `document.body`, uses lowercase tags and same-tag sibling ordinals, and excludes controls by shim ownership. Resolution walks elements directly and requires the exact `IMG` and matching digest. The digest covers authored `src`, `srcset`, `sizes` and ordered immediate-picture source declarations, preserving absent versus empty attributes. It never contains image bytes or uses `currentSrc` or alt text as identity. There is no nearest-image, coordinate or source-search fallback.

The frame receives locators and comment IDs, never bodies or keys. Placement acknowledgments must match the current frame, live comment and latest request ID. Unavailable placement removes stale geometry and marks the readable thread unplaceable. An unavailable pending target retains its draft but refuses image-targeted submission until re-aimed or cleared. Replies update geometry only and never reopen a dismissed card. Actual edge controls and badges supply attachment rectangles; full-image outlines do not intercept input. Load, resize, nested scrolling and author reflow refresh geometry. Thread activation reveals the image and obtains fresh placement before opening.

**A comment is written in a panel attached to its target, on every class, and the posted comment stays there.** For a verified reader, every gesture that sets a target on the stage opens the shared stage composer (`openComposer`, `inlineComposer`) beside that target: **Comment** on a selection offer, in the page or inside a frame; a point placed or a box drawn while pointing is armed, by pointer, touch or keyboard; a box dragged on a PDF page; a moment or span on the media scrubber; and a point, range or track selection on an OpenTimelineIO rail. While the panel is open its target is painted, as the provisional mark, the scrubber's pending span or the painted `.otio-selection`, and the panel names it. On a document the panel goes above the target by preference, because a panel below covers what the reader reads next; on a timeline it goes below by preference, because the picture under review sits above the timeline. Either flips when its side does not fit, and the panel never covers its target: when neither side holds the whole panel, the layer caps its height on the larger side and the context scrolls while the field, **Post** and **Cancel** stay on the card. A target taller than half the visible stage is attached by its first line, or by its top edge when it has no lines. The panel follows its target, measured live, when something inside the stage scrolls or when the frame of an `html`, `jsx` or `svg` relic scrolls, and it holds still while the target is out of view. Posting replaces the composer with the posted comment's card on its new mark, with **Reply**, **Edit**, **Resolve** and **Open in thread**, and focus moves into the card. The Comments sidebar is left exactly as it was, because below 44rem an open sidebar takes the whole row and would hide the comment just written. A mark's card opens the same way: after `MARK_HOVER_OPEN_MS` on hover, and pinned by a click, a tap or keyboard focus, and Enter on a focused pin or timeline marker moves focus into the card. Pressing a mark opens its card and nothing else; only **Open in thread** opens the sidebar. Escape and **Cancel** discard a draft and return focus to where the composer was opened, and a press elsewhere keeps a composer that holds text. A reader with no verified address is still sent to the sidebar, where the address is verified.

**Comment bodies are ciphertext to the operator, under a key the fragment already carries.** A comment about content the operator cannot read, stored in the clear, hands the operator exactly what the architecture exists to deny. The comment key is HKDF-SHA256 over the same 16 fragment bytes under a distinct `info`, which is the mechanism `rfc8188.ts` already uses to get a content key and a nonce base out of one input. **The fragment does not change**, and that matters: `format.md` 2.1 says the fragment carries exactly two things and a third field takes a version bump. A third `info` string is not a third field.

**Reading the thread needs no authorization and that is deliberate.** Anyone holding the link can already read the content, and the bodies are ciphertext the server cannot open, so a gate on the read would protect nothing and would turn an unauthenticated reader into somebody who cannot see that a thread exists.

**Private comments are per version, and reading them needs access.** The key rule above is for public relics. For a private relic each comment is encrypted and decrypted under the comment key of its own version, not under a fragment key (plan correction 10). A private comment read requires a session with access and returns only comments on versions that session can read, so the reading rule above does not hold for private relics. A private comment write names a version and needs a wrap for it, or the publish token. A row that will not decrypt is shown as undecryptable, as state 4 above says, and is never dropped.

**Ten states, and every one of them has copy.**

1. **Loading**, with its reason attached rather than a bare spinner. The bodies arrive as ciphertext and are opened in this browser, so the list can exist before the words in it do, and the copy says exactly that. No spinner without a reason is the rule §6.4 already set for the three fetch phases, applied here.
2. **Empty.** "No comments yet." followed by what a comment is for and what happens to it, because an empty thread is a state and not an error. It does not overclaim: the sentence is that Relic stores the text without being able to read it.
3. **A thread with comments**, oldest first, each carrying the verified address, the optional display name in front of it, and an absolute timestamp. Relative times are wrong here on purpose: a relic is a catalogued object and "3 hours ago" on a page opened next month is worse than useless.
4. **A comment that will not decrypt is shown as undecryptable, never dropped.** It keeps its author and its time and loses only its body. Dropping it would tell the reader the thread is shorter than it is, which is a lie one bad stored row could induce, and the copy names both plausible causes without claiming to know which: written under a different key for this relic, or altered in storage. That is the same honesty §6.1 item 4 puts on a content decrypt failure.
5. **A row that arrives without a ciphertext at all is reported as unreadable, in its own state rather than as sealed.** Sealed means there was a body and it would not open under this relic's comment key. Unreadable means the row did not arrive in a shape the page can read, so there may never have been a body, and calling that sealed would be a guess about what went missing. **An earlier version of this item said such a row was skipped. That is reversed**, because skipping it is the same shortened-thread failure item 4 exists to prevent: the reader sees a complete thread that is not complete and has no way to notice. It counts in the total, it shows whatever the row did carry, and where the row named no sender the page leaves that slot empty rather than inventing one.
6. **Refused**, with the server's code stated verbatim rather than flattened into an apology, exactly as §6.1 item 3 requires of a refused mint. A retry appears only where pressing it again could plausibly work.
7. **Legacy comment-rate refusal**, retained for older servers: the viewer names the refusal and offers a retry. Current servers do not rate limit comment writes.
8. **Unverified**, where the composer asks for an address.
9. **Waiting on a link or code.** The request endpoint answers 202 whether or not anything was sent, so it cannot be used to find out who has commented before, and **the copy must not undo that**: it says that if the address can receive mail an email with a code and a link is on its way, and it never confirms the address exists.
10. **Verified**, where the composer names the address it will attribute the comment to, before anything is typed.

**The disclosure is at the point of commenting, not only on the policy page.** A reader learns, above the fields and at reading size rather than as fine print, that their verified address is shown with their comment and in emails to people following the relic, that commenting signs the address up for an email whenever someone comments or a new version is published, each with a stop link, that Relic can see which address commented on which relic, and that a display name sits beside the address rather than instead of it. A second line, at the address field, says that sending the sign-in email means handling the address in plain text and that it cannot be done any other way. Both are `frame.md`'s prices, stated where they are actionable. A person should learn this before they submit, not after.

**The display name is untrusted display text and gets §1.9 rule 2's treatment.** It is chosen by whoever holds the link and rendered on the origin that holds the fragment, which is the filename's situation exactly, so the bidirectional formatting characters are stripped rather than escaped. The author runs through the same filter: the server verified that a mailbox answered, which says nothing about how the string draws.

**The magic-link and code round trips must not cost the reader the key, and the fragment is never what carries it back.** The server has never seen the fragment and cannot put it in a redirect or mail it, so nothing on the return path can restore it from the wire. Typing the code keeps the reader on the page with zero navigation, so the key never leaves tab memory. When following the link instead, what restores it is the key vault: `load` writes the fragment to storage after a successful mint, so a tab that navigates to the callback and comes back to `/{id}` with no fragment recalls it there, exactly as a reload already does. Four consequences:

- **The auth request carries an address and a relic id, and nothing else.** The relic id is how the callback knows where to send the reader, and the server already has it on every request to this relic. The fragment is not in the body, not in a query string, and not in the return path.
- **The redirect stays inside the service and therefore omits the fragment**, which is §1.7's inside-the-service half rather than its leaving-the-service half. There is nothing to inherit, and an explicit empty fragment would be worse than nothing: it would strip a key the vault was about to restore.
- **The common case never navigates at all.** A reader types the six-digit code directly into the requesting page, or opens the link in a mail client tab while the relic page stays in place with its key in memory. When using the link in another tab, the relic tab learns it is verified from a same-origin broadcast carrying a bare marker, no address and no key, and from a re-check when the tab becomes visible again. Neither signal touches the URL.
- **When this browser is not keeping the key, the reader is told before they leave.** Storage can be absent or refuse to write, and in that case following the link in the same tab loses the key for good. The composer says so, and advises typing the code from the email right here, or opening the link in a new tab and coming back to the one that still holds the key in memory. Discovering it afterwards is the §6.1 missing-key screen, which is honest and much too late.
**Two authentication paths exist and only one of them is a browser.** A verified session is the human path. The publish token is the agent and publisher path, attributed as `publisher`, and it is not offered here: the token lives on the publishing machine and a field for it on this origin would be the key-entry surface §6.4 bans, aimed at a different secret. A comment attributed to `publisher` is marked as having published the relic, which is true by construction rather than by claim, since only the machine that published it holds a token.

### 6.7 The landing page at `/` and `/install`

The PWA manifest's `start_url` is `/`, so an installed app launched cold landed on that same broken screen, which is the opposite of the neutral page §6.4's PWA case calls for. **Script-free on both routes: the 2026-10-06 reversal is itself reversed on 2026-11-05.** The landing page was originally script-free under a strict CSP denying scripts (`default-src 'none'`). Jason Waldrip authorised script on `/` on 2026-10-06 so the homepage could list the relics this browser had opened. - **The disclosed cost is gone, not accepted.** The homepage again runs no code on the origin where local decryption keys reside, which is the posture §6.7 originally held.

Said plainly, because it reads backwards: a landing page is normally the one page an origin wants indexed, and keeping it unindexed is a consequence of the origin-wide posture, not a judgement reached here. Revisiting it means reopening the precondition, not editing this page.

**`/policy` opens in the markdown player, and is not a relic.** Requested by Jason Waldrip on 2026-11-05. **The markdown player exports a document as a PDF or a Word file, in the browser.** Requested by Jason Waldrip on 2026-11-11. ### 6.8 The share action and point-of-sharing disclosure

A reader holding the link and decryption key can share a relic from the viewer.

**Gated by key proof and verified sign-in.** Sharing requires an authenticated session (reusing the comment session flow). The viewer derives the 32-byte share proof from the fragment key with `deriveShareProof` (`format.md` 3.14) and submits `{ share_proof, emails }` to `POST /api/relics/{id}/share` for up to 20 addresses.

**For a private relic the share action is an access check, not key proof.** The reader needs a session with access to the relic (6.12), and the submission to `POST /api/relics/{id}/share` carries `emails` with no `share_proof` (plan 4.7).

**The disclosure is at the point of sharing.** Before submitting addresses and when reviewing the composed email, the share panel states prominently:
- Relic never sends this email.
- For a public relic, the link in it carries the key. A private relic's link carries no key, and each reader it lets in holds their own key.
- Relic stores these addresses in the clear to email them when someone comments or a new version is published, each with a stop link.
- For a private relic, Relic's notices say only that there is activity on the relic. Private mail names no title, and no address other than the recipient's (plan 4.14).

**Composed email handoff.** After the server accepts the addresses, the viewer displays the composed message produced by `composeShareEmail({ sender: 'reader', ... })` from `@relic/format`, offering "Open in your mail app" (`shareMailtoUrl`) and "Copy message". The reader sends the email from their own mail client, so the full URL containing the decryption key never touches the server.

For a private relic the message is composed with `access: 'private'`, so it carries the keyless link only (plan 4.16).

**Refusal presentation.** Every server refusal is rendered with actionable guidance:
- `401 sign_in_required`: Prompts the reader to sign in (link or passkey) before sharing.
- `409 share_unavailable`: Displays the server's explanation: "This relic was published before sharing existed. Its publisher can republish it to turn sharing on."
- `400 invalid_share`: Explains that the email list or proof was malformed or exceeded the per-call cap of 20 addresses.
- `403 invalid_share_proof`: Indicates the key proof does not match the published verifier.
- `409 share_limit_reached`: Explains that the relic has reached its maximum of 50 shared addresses.
- `429 share_rate_limited`: Explains the rate limit and provides the retry time.


### 6.9 The decision stamp

A reader holding the link and decryption key can record an approval or rejection decision on the rendered version of a relic, and view decisions recorded by others.

**Decisions are distinct from comments.** Commenting is discussion and feedback. An approval decision is a deliberate, first-class act in the viewer that downstream systems (such as Backlot) rely on to authorize execution. Comments never mean approval, and no comment text creates a decision.

**The taskbar control and tally.** The taskbar carries a dedicated Decisions button (`button.action-decisions[data-decision-open]`, icon mark `stamp`), displaying the current tally of approvals (`data-decision-approvals`) and rejections (`data-decision-rejections`) on renderable relics. Clicking it opens the decision panel (`dialog.decision-panel[data-decision-version]`).

**Listing decisions on the current version.** Opening the panel lists all recorded decisions for the active version being viewed, fetched via `POST /api/relics/{id}/decisions/list` with `{ share_proof, version: activeView.version }`. Each row (`[data-decision-row][data-decision-author][data-verdict]`) shows the author's verified address, the verdict (Approved or Rejected), and the timestamp.

For a private relic, the decision options, record and list carry no `share_proof`. The access check and the session's identity authorize them instead (plan 4.7). `decisions/list` also accepts the publish token from relic-mcp.

**The ceremony flow:**
1. *Sign-in check:* If the reader has no verified session cookie, the panel mounts the sign in (link or passkey) form (`[data-decision-signin]`).
2. *Verdict selection:* The reader selects a verdict via `[data-decision-verdict="approve"]` or `[data-decision-verdict="reject"]`. Selecting a verdict immediately fetches challenge options from `POST /api/relics/{id}/decisions/options` presenting `{ version, verdict, share_proof }`.
3. *Passkey enrollment (TOFU):* If the options endpoint returns `409 passkey_required`, the panel shows the passkey setup step (`[data-passkey-create]`). The reader registers a WebAuthn passkey via `POST /api/auth/passkeys/options`, `navigator.credentials.create()`, and `POST /api/auth/passkeys`. Once registered, the panel re-fetches decision options. If `POST /api/auth/passkeys/options` answers `401 passkey_fresh_link_required`, the step becomes `section.decision-passkey[data-passkey-link][data-state="required"]`: it keeps the session, says a first passkey can only be added right after signing in with a link, and its `[data-passkey-link-send]` button asks the shell to email a new link to the session's address (`data-state` `sending`, then `sent` or `failed`).
4. *Content digest verification:* The viewer verifies that `options.version_digest` matches `view.versionDigest` (the SHA-256 of the ciphertext bytes downloaded and decrypted by the viewer). If they diverge, the panel displays mismatch copy (`[data-decision-outcome][data-state="error"][data-code="decision_digest_mismatch"]`: "The file stored for version N is not the file this page shows. Nothing was recorded.") and halts the ceremony without invoking WebAuthn.
5. *Synchronous user gesture and confirmation:* To satisfy browser user-activation rules (such as Safari's requirement that credential requests execute synchronously within a user gesture), `navigator.credentials.get()` is invoked synchronously inside the click handler for the Confirm button (`[data-decision-confirm]`), passing the pre-fetched public key options.
6. *Recording the decision:* The assertion response is submitted to `POST /api/relics/{id}/decisions` with `{ version, verdict, share_proof, version_digest, credential }`.
7. *Outcome:* Upon receiving `201`, the panel displays the recorded outcome stamp (`[data-decision-outcome][data-state="recorded"]`), refreshes the decisions list, and updates the taskbar tally.

**Version scoping and stale view notice.** Decisions apply strictly to the specific version rendered. When viewing an older version on a relic that has been republished, the panel displays a prominent notice (`[data-decision-stale]`): "You are viewing version N. Version M is the newest. A decision here applies to version N only."

**Refusal presentation:**
- `401 sign_in_required`: Prompts the reader to sign in (link or passkey).
- `409 passkey_required`: Prompts passkey enrollment.
- `409 passkey_assertion_required`: Explains that adding another passkey requires confirmation with an existing one.
- `401 passkey_fresh_link_required`: Shows the new-link step (`[data-passkey-link]`) and keeps the session. Nothing was recorded.
- `409 decision_unavailable`: Displays: "The publisher has not asked for decisions on this relic." The band's Decisions control is drawn only once the list has landed, so a relic whose author did not ask for decisions never shows it; this copy covers a refusal that arrives after the sheet is open.
- `409 decision_digest_mismatch`: Displays: "The file stored for version N is not the file this page shows. Nothing was recorded."
- `403 invalid_share_proof`: Indicates that the key proof did not match the relic's verifier.
- `429 decision_rate_limited`: Explains that too many decision requests were made and provides retry time.

### 6.10 Passkey sign-in and the offer after a sign-in email

Returning readers can sign in with a passkey without receiving an email. Readers signing in via an email link or a typed code are offered passkey enrollment after signing in.

**Autofill and conditional mediation.** On forms where readers authenticate (`signInForm` in comments, share, decision panel, and dashboard), the email field carries `autocomplete="username webauthn"`. When WebAuthn is supported and the context is secure, the client dynamically loads the passkey sign-in module. A module-level ceremony controller fetches usernameless public key options from `POST /api/auth/passkeys/sign-in/options` with `{}` and arms a conditional request (`navigator.credentials.get({ mediation: 'conditional', ... })`).

**The page-wide ceremony abort rule.** Only one WebAuthn ceremony can be pending per page at any time. Any new ceremony (a button press, an email-first confirm, or a decision assertion) aborts the prior ceremony via an `AbortSignal` before starting. AbortError resulting from this internal replacement is swallowed silently. Options refresh before the challenge timeout (300 seconds), only while the page is visible. When authentication occurs (such as via a magic-link callback in another tab broadcasting `relic:auth`), pending ceremonies are aborted.

Identity ceremonies for private relics (6.12) are WebAuthn ceremonies under this rule as well, so starting one aborts any pending ceremony on the page.

**The usernameless button and modal gesture.** Beside the email field and send button, the interface renders a "Sign in with passkey" button (`button.action.passkey-button[data-passkey-sign-in]`). Clicking the button aborts the background conditional request and immediately calls `navigator.credentials.get()` synchronously inside the click handler using the pre-fetched options. On success, the assertion is posted to `POST /api/auth/passkeys/sign-in`, setting the session cookie and transitioning the interface to the signed-in state without an email.

**The email-first fallback.** If a reader's passkey is non-discoverable, or if usernameless sign-in fails (`401 passkey_sign_in_failed`), the interface reveals the fallback option (`[data-passkey-fallback]`). The reader enters their email address and clicks "Use a passkey for this address". The client fetches options for that address via `POST /api/auth/passkeys/sign-in/options` with `{"email": "<address>"}`, which returns descriptors padded with HMAC decoys. The reader confirms with their passkey synchronously, and the assertion is posted to sign in.

**The post-sign-in passkey offer.** When a reader completes a magic-link sign-in or types a sign-in code, the service sets a short-lived `relic_passkey_offer=1` cookie. When the viewer boots (or when the composer completes an in-place code sign-in), if the marker cookie is present, the session is verified, and local storage does not contain `relic:passkey-offer`, the viewer consumes and clears the marker cookie and mounts the offer card (`section.passkey-offer[data-passkey-offer]`). The offer mounts on boot and on in-place code sign-in completion; ordinary tab visibility re-checks do not mount it if the marker was already consumed or dismissed.
- *First passkey (TOFU):* Prefetches create options from `POST /api/auth/passkeys/options`. Clicking "Add a passkey" invokes `navigator.credentials.create()`, posts the registration to `POST /api/auth/passkeys`, and stores `'created'` in `localStorage['relic:passkey-offer']`. If the options call answers `401 passkey_fresh_link_required`, the card moves to `data-state="link-required"` instead of closing: it hides `[data-passkey-offer-create]` and shows `[data-passkey-offer-link]` ("Send me a new link"), which asks the shell to email a new link to the same address (`link-sending`, then `link-sent` or `link-failed`). A `401` with any other code still closes the card.
- *Every new passkey requests PRF at creation:* the creation options carry `extensions: {prf: {}}` (plan 4.7). The [WebAuthn Level 3](https://www.w3.org/TR/webauthn-3/) `prf` extension returns output only when a relying party asks for it, and a credential created without it returns no PRF output (plan appendix, measured in Chrome 157 and HeadlessChrome 149). A credential that gives no PRF output on an assertion is handled by the private setup flow in 6.12, not by this card. PRF results are never sent to the service.
- *Device with existing passkeys elsewhere:* The options endpoint returns `mode: 'assert'`. The reader first confirms with their existing passkey, then adds a passkey on this device.
- *Dismissal:* Clicking "Not now" stores `'dismissed'` in `localStorage['relic:passkey-offer']`, suppressing future offers in this browser.

### 6.11 The sign-in code

Alongside the single-use magic link, every sign-in email carries a six-digit decimal code. The reader can type the code directly into the requesting page to sign in without leaving the tab, preserving the decryption key in memory and avoiding tab switches.

**The DOM structure.** The code entry control renders inside `.sign-in-code`:

```html
<div class="sign-in-code" data-sign-in-code="" data-state="idle">
  <label class="compose-field sign-in-code-field"><span>Code from the email</span>
    <input class="compose-input sign-in-code-input" data-sign-in-code-input="" type="text"
      inputmode="numeric" autocomplete="one-time-code" autocapitalize="off" spellcheck="false"
      enterkeyhint="go" aria-describedby="sign-in-code-status-{n}"></label>
  <button type="button" class="action primary sign-in-code-submit" data-sign-in-code-submit="" disabled>Sign in</button>
  <p class="sign-in-code-status" data-sign-in-code-status="" id="sign-in-code-status-{n}" role="status" aria-live="polite"></p>
</div>
```

The input deliberately omits `required`, `pattern`, or `maxlength` attributes so that enclosing forms (such as the dashboard sign-out form) are never blocked from submitting by the nested code field.

**States and copy.** `data-state` takes one of `idle`, `checking`, `rejected`, `rate-limited`, `failed`, or `verified`:
- **Idle:** button is disabled until exactly six normalized digits are entered.
- **Checking:** input and submit button are disabled. Status displays "Checking the code."
- **Rejected:** status displays "That code did not work. Check it against the newest email from Relic, and type it in the browser that asked for it." Upon a third rejection, the copy escalates to: "That code still did not work. A code works once, only in the browser that asked for it, and stops working after a newer email or too many wrong tries. Open the link in the email instead, or send a new one." The input is re-enabled and selected for immediate retyping.
- **Rate-limited:** status displays "Too many codes tried from here. Wait about N minutes, or open the link in the email." (or "Wait a few minutes..." when retry seconds are unspecified).
- **Failed:** network or server error copy: "The code could not be checked, which is a network problem rather than a wrong code. Try again."
- **Verified:** status displays "Signed in as <address>." Controls are disabled, and `onVerified` executes.

**Input normalization and auto-submission.** Input strips ASCII spaces and hyphens. When the normalized value reaches six digits and differs from the last submitted value, it auto-submits immediately. Pressing Enter always executes `preventDefault()` and submits if six digits are present, preventing outer form submissions.

**Browser binding and cookie scoping.** The typed code works only in the browser that requested the email. When the reader requests sign-in, `POST /api/auth/request` sets an HttpOnly, Secure, SameSite=Strict cookie `relic_sign_in_request` scoped to path `/api/auth/code`. Submitting the code sends only `{"code": "123456"}` with this cookie. A code entered in another browser or after a newer request in the same browser fails with uniform 401 `sign_in_code_failed`.

**Per-surface behavior:**
- *Comment composer:* appears in the sent state after the email message and warning note. Focus is set automatically in a microtask. Upon verification, sets session attribution, clears the code block, mounts any owed passkey offer, announces verification across tabs, and enables comment submission.
- *Passkey offer card:* when requesting a fresh sign-in to enroll a first passkey, the card renders the code entry in `link-sent` under `[data-passkey-offer-code]`. Upon verification, empties the container, transitions to `loading`, and fetches creation options.
- *Decision panel:* renders the code entry in the `sent` step of passkey link creation. Upon verification, immediately invokes `enterPasskey(verdict)`.
- *Dashboard:* displays the code entry under the sent notice. Upon verification, announces across tabs and reloads the page to show the verified session and passkey enrollment card.

### 6.12 Private relics: reader, owner and dashboard

A private relic's link is `https://<relic-domain>/{id}` with no fragment. Its key is not in the URL, so the viewer takes every key from the reader's own passkey and every state from the server. This section is the viewer's side of the private-shares build plan (`docs/plans/private-shares/README.md`, sections 4.4, 4.7, 4.13 and 4.15). The DOM hooks named here are exact.

**Access declaration and states.** The shell root carries `data-relic-access="private"` for a private relic, also when the relic has expired. The viewer reads that declaration and `GET /api/relics/{id}/access` (`PrivateAccessJSON`, with `me.role`, `sealed_version`, `readable_versions` and `owner`). For a private relic it never reads the fragment, and it never shows the missing-key state of 6.1. The host is `#relic-private[data-private-state]`, whose values are `signin`, `setup`, `setup-refused`, `replace-offer`, `request`, `requested`, `declined`, `unlock`, `ready`, `revoked`, `denied`, `owner-changed` and `seal-mismatch`. Plan 4.15 names those states without mapping each one from the declaration, so that mapping is an open item below.

**Reader path.**

1. **Sign in.** A reader without a verified session signs in first, by passkey, link or code, as 6.10 and 6.11 describe. Passkey sign-in does not unlock the identity, which takes its own PRF tap.
2. **Identity setup** (`[data-action="private-setup"]`, state `setup`). Setup asks for one assertion with `userVerification: 'required'` that returns a PRF result, and sends nothing unless that result comes back (plan 4.4). The requirement is the PRF result from an assertion. A creation response that reports `enabled: false` is an early refusal only, because `enabled` is advisory (plan section 2, correction 3). Setup tries PRF on the reader's existing credentials first. If none answers, it shows `replace-offer` with this copy: "This passkey was made before private shares existed and can't hold your key. Make a replacement passkey on this device?" The action `[data-action="private-replace-passkey"]` creates the replacement with `extensions: {prf: {}}` and an empty exclude list, then retries setup once. A second miss shows `setup-refused` with this copy: "Your passkey provider can't hold a private-share key. Private relics need a provider or security key that supports the WebAuthn PRF extension." Setup does not retry after that refusal. The `prf` extension is defined in [WebAuthn Level 3, section 10.1.4](https://www.w3.org/TR/webauthn-3/#prf-extension).
3. **Request** (`request`, action `[data-action="private-request"]`). The reader sends a signed `access_request` (plan 4.3). The screen shows the reader's own fingerprint: 32 characters in display format, computed locally from public keys, since no API returns a fingerprint (plan 4.2). The copy beside it is: "Read this fingerprint to the person who shared the link, on a phone or video call. Don't send it by email or chat: it only protects you if it travels a different way than this site." The state is `requested` while the request is pending, and `declined` if the owner declined it. The requester's fingerprint is one of the four `data-fingerprint` hooks (`mine`, `owner`, `identity`, `owner-for-device`), which plan 4.15 says hold display-format text but does not bind to a screen (open item).
4. **Unlock** (`unlock`, action `[data-action="private-unlock"]`). One tap: a local random challenge, `allowCredentials` set to the identity's bound credentials, and PRF evaluation. The viewer decrypts that credential's bundle, imports the JWKs as non-extractable keys, and checks that the imported public keys hash to the expected `identityId`.
5. **Open a version** (`ready`). The reader opens the highest sealed version they can read, never an unsealed one (plan section 3, decision 5). Before any content renders, the viewer verifies each of the following and refuses when one fails:
- the wrap opens with the reader's KEM key;
- the seal's signature chains to the owner identity, whether the signer is a device or an identity;
- the recipient list contains the reader's `kemKeyId`;
- the ciphertext SHA-256 equals the sealed digest;
- the owner identity matches the one pinned for this relic in `localStorage['relic:private-owner:<id>']` at first open (plan section 3, decision 4).
The pin is set at first open and never changes. A pin mismatch is a hard refusal in state `owner-changed`, with this copy: "The owner's key for this relic isn't the one you saw when you first opened it. Relic won't open it. Contact the person who shared it." It has no "accept new owner" control. A failed seal check (signature, digest or recipient list) refuses in `seal-mismatch`, with this copy: "This version doesn't match the owner's signature. Relic won't show it." The plan says each check refuses but does not say which state each failure uses beyond these two (open item). The record-0 key check of 6.4 describes public relics and does not apply here.
6. **Revoked and denied.** `revoked` and `denied` are named states of plan 4.15. The plan gives no copy for either, so none is quoted here.

**Vault and key exclusion.** A private relic is never written to the local key vault, and the viewer never offers a key phrase or a key-bearing link for it (plan 4.13). The vault paths of 6.4 and 6.6 do not apply to a private relic. No private flow sends PRF output, key material or `clientExtensionResults` in any request body (plan 4.4, correction 19).
**Expiry.** A private relic always expires. The server stops serving it at expiry, and its mint refuses with the server's reason, as 6.1 item 3 describes. One day after expiry the bucket removes the live objects (`storage.md` section 7.2, plan decision 7). Deleted copies stay restorable by the operator under the soft-delete retention, so the reader-facing state does not describe removal from storage.

**Owner panel.** The owner opens the access panel with `[data-action="open-access-panel"]` on a private relic they own. The hooks, from plan 4.15, are:
- each pending request: `[data-request-identity="<identityId>"]`;
- the typed fingerprint, `input[data-fingerprint-input]`, whose state is `[data-fingerprint-state="empty|mismatch|match"]`. The typed value is normalized as plan 4.2 says (whitespace and hyphens removed, lowercased, `i` and `l` folded to `1`, `o` folded to `0`, 32 characters required) and compared with the locally computed fingerprint in constant time;
- the version picker, `input[data-grant-version="<n>"]`, on which the current version is locked on (plan S0 mock);
- `[data-action="grant"]`, disabled unless the fingerprint state is `match`. The grant is one tap: the owner unlocks the owner identity with PRF and attests the grant, so the assertion commits to the grant record (plan section 2, correction 8). It wraps each selected version to the grantee's key;
- `[data-action="decline"]` on a request;
- for each active grant, `[data-grantee="<identityId>"]` and `[data-action="revoke"]`. Opening revoke shows this warning before anything is sent: "Revoke {email}? Relic stops serving them this relic now and deletes their keys for it. Anything they already opened may still be on their device. The current content is republished as version {n} under a new key that only the remaining readers can open." `[data-action="confirm-revoke"]` is the only control that sends it;
- rekey progress, `[data-rekey-state="decrypting|encrypting|uploading|sealing|done|failed"]`. The browser decrypts each version with `fetchAndDecryptVersion`, encrypts once under a fresh key with the original filename and mimetype, PUTs to the signed URL, seals under the owner identity, and completes. Wraps go only to the remaining recipients, and the browser never holds the publish token (plan correction 12, S5);
- `[data-action="delete-relic"]`, `input[data-delete-version="<n>"]` and `[data-action="confirm-delete"]`, for owner hard delete (plan 4.7).

**Dashboard.** The dashboard is `[data-private-dashboard]`. The hooks, from plan 4.15, are:
- device approval at `/dashboard?approve-device=<enrollmentId>` (plan section 3, decision 10): `[data-device-approval="<enrollmentId>"]`, `input[data-device-fingerprint-input]`, checked against the device's locally computed fingerprint, and `[data-action="approve-device"]`, which refuses a mismatch. After approval the owner fingerprint is shown at `[data-fingerprint="owner-for-device"]` for typing into relic-mcp's `relic_confirm_device` (plan correction 6);
- devices: `[data-device="<deviceId>"]` and `[data-action="revoke-device"]`;
- recovery: `input[data-recovery-email]` with `[data-action="recovery-lookup"]`, then `input[data-recovery-fingerprint-input]` with `[data-action="designate-recovery"]`. A designation is an identity-signed `recovery_designation`. Versions sealed before it are backfilled from the owner's browser through `/api/identity/backfill` (plan correction 17);
- coverage: `[data-action="repair-coverage"]` reads `GET /api/identity/relics?coverage=1` and backfills the gaps it reports (plan 4.12);
- the access log: `[data-access-log] [data-access-event="<kind>"]`, where `<kind>` is `request`, `grant`, `revoke`, `wrap_fetch` or `delete` (plan 4.6);
- retention: `input[data-retention-days]` with `[data-action="save-retention"]`, signed as `identity_settings`. The default is 2190 days, the minimum 30 and the maximum 3650 (plan 4.9 and section 10);
- the identity card with passkey binding, which takes two taps (plan 4.4), and the owned and shared relic lists from `GET /api/identity/relics`. Plan 4.15 names no hook for these, so the mock (S0) is their reference.

**Open items.** Plan 4.15 and sections 2 to 10 leave each of these undecided here:
- the mapping from the access declaration (`PrivateAccessJSON`) and the reader's local state to each `data-private-state` value;
- the screen each `data-fingerprint` hook (`mine`, `owner`, `identity`, `owner-for-device`) holds;
- the state a seal-check failure uses other than the owner pin. The plan names `seal-mismatch` for the signature copy only;
- what a reader sees for an expired private relic once its live objects are removed. The plan names no copy for it;
- copy for `revoked` and `denied`.

## 7. Routed to `shape`

Five items, and only these five.

1. **Browser memory behavior.** Browser-managed Blob backing and device
   limits vary; the earlier whole-file memory ceiling is superseded (§5).
2. **The hard size cap.** 500 MiB of plaintext; the ciphertext bound is
   derived from the current framing.
3. **Large source.** A windowed source view reaches the full file above
   100 MiB rather than stopping at a truncated prefix.
4. **Highlighted-region cap.** The original proposal is historical; large
   source windows are plain text.
5. **PSL registration for the usercontent parent.** **Lead time: there is none published, and that's the finding rather than a gap in the research.** The list's own guidelines state "There are NO SERVICE LEVEL AGREEMENTS ON TIME nor any expectation of processing speed or urgency," and on reaching production, "Unfortunately, there is no way to expedite," because propagation rides each browser and OS vendor's release train ([PSL guidelines](https://github.com/publicsuffix/list/wiki/Guidelines)). Unbounded and unexpeditable makes it the first thing started in the domain workstream, ahead of work that looks more urgent.

## 8. What this document needs from `spec-service-surface`

Stated as needs. That sibling defines the mint response.

1. **The signed URL.**
2. **Its absolute expiry**, so repeat opens can tell whether reuse is valid instead of minting again (§6.4).
3. **Object length in bytes**, for the refuse-before-allocating check (§5) and for a real total on the fetching phase (§6.4).
4. **The object's CRC32C checksum**, which is what separates transport corruption from a wrong key (§6.1).
5. **A machine-readable refusal reason on a refused mint**, distinguishing enough cases that state 3 shows a real reason rather than a generic failure. The set of reasons is that sibling's to define, not this one's. `format.md` §1.2 already permits distinguishing an expired relic from one that never existed, so at least that pair is available to it. Expiry is no longer universal: the expired-relic state is reachable only when the publisher set a lifetime, and a relic without one never produces it, so the refusal-reason surface covers both a stated lifetime and its absence.
6. **The private access declaration.** The shell root carries `data-relic-access="private"`, also when the relic has expired. `GET /{id}` for a private relic serves the generic card, with no title, no cover and no renderer-class copy. `GET /api/relics/{id}/access` returns `PrivateAccessJSON` and answers 401 without a session for a private relic (plan 4.7). Sections 6.1, 6.2 and 6.12 need each of these.
7. **Private mint and key routes.** Mint for a private relic requires a session whose identity holds a wrap for the version, or the publish token, and the version must be sealed and not deleted. `POST /api/relics/{id}/versions/{v}/key` returns the reader's wrap, seal, signer and owner for a readable version, and refuses `403 private_access_denied` otherwise. The owner panel and dashboard call the identity, request, grant, revocation, delete, device and access-log routes of plan 4.7. Sections 6.4, 6.6 and 6.12 need each of these.
